# 任务四 静态链接生成执行程序答案

## 静态链接与动态链接生成的可执行程序的差异

为了比较静态链接与动态链接生成的可执行程序差异，可以先分别生成两个版本：

```bash
gcc -g -D U2 main.c sub.c -o main_sub_dyn
gcc -g -static -D U2 main.c sub.c -o main_sub_static
```

再结合以下命令进行观察：

```bash
ls -lh main_sub_dyn main_sub_static
file main_sub_dyn main_sub_static
ldd main_sub_dyn
ldd main_sub_static
readelf -d main_sub_dyn
readelf -d main_sub_static
objdump -d main_sub_dyn
objdump -d main_sub_static
```

结合本实验的结果，可以从以下几个方面来比较。

### 1. 文件大小差异明显

本实验中，动态链接生成的 `main_sub_dyn` 大小约为 `20K`，而静态链接生成的 `main_sub_static` 大小约为 `884K`。两者相差很大，根本原因在于：

- 动态链接生成的可执行文件，只保留用户程序本身的代码，以及运行时加载共享库所需的信息；
- 静态链接生成的可执行文件，会把程序运行所需的库函数实现直接拷贝到可执行文件内部。

本程序中使用了 `printf`、`strlen`、`exit` 等标准库函数。动态链接时，这些函数的真正实现仍然保存在系统的共享库 `libc.so.6` 中；而静态链接时，链接器会把相关实现从静态库中复制到程序里，所以最终文件会明显增大。

### 2. 对外部运行环境的依赖不同

使用 `file` 和 `ldd` 可以看到：

- `main_sub_dyn` 是 `dynamically linked`，并依赖 `/lib64/ld-linux-x86-64.so.2` 和 `libc.so.6`；
- `main_sub_static` 是 `statically linked`，`ldd` 的结果为 `not a dynamic executable`。

这说明动态链接程序在运行时仍需要系统提供相应的共享库和动态加载器；如果系统中缺少兼容版本的共享库，程序可能无法正常运行。静态链接程序则把所需库代码打包进自身，因此自包含程度更高，运行时对外部共享库的依赖更小。

### 3. ELF 文件内部结构不同

动态链接版中可以看到明显的动态链接相关节和动态段，例如：

- `.dynsym`
- `.dynstr`
- `.rela.dyn`
- `.rela.plt`
- `.dynamic`

并且 `readelf -d main_sub_dyn` 可以看到 `NEEDED` 条目，其中明确指出需要 `libc.so.6`。

而静态链接版中，`readelf -d main_sub_static` 的结果显示：

```text
There is no dynamic section in this file.
```

这说明静态链接生成的可执行文件不需要依赖动态链接器在运行时继续解析共享库，因此不再需要 `.dynamic` 这一类动态链接信息。

### 4. 函数调用方式不同

这一点可以通过反汇编看得最清楚。以 [main.c](main.c#L29) 中 `fcount` 函数对 `printf` 的调用为例。

在动态链接版中，反汇编结果为：

```text
1209: e8 b2 fe ff ff          call   10c0 <printf@plt>
```

这里调用的不是 `printf` 的真正实现，而是 `printf@plt`。`PLT` 是过程链接表，它的作用是为动态链接函数提供跳转入口。程序运行时，再由动态链接器结合 `GOT/PLT` 机制找到 `printf` 在共享库中的真实地址。

而在静态链接版中，对应位置变成了：

```text
4017b5: e8 66 a1 00 00        call   40b920 <_IO_printf>
```

这说明静态链接时，`printf` 的实现代码已经被直接放入了本程序内部，因此这里不再经过 `printf@plt`，而是直接调用程序中已有的库函数实现。

所以可以概括为：

- 动态链接：调用共享库函数时往往先经过 `PLT`；
- 静态链接：调用的往往是已经并入程序内部的实际库函数代码。

### 5. 代码共享与维护方式不同

动态链接的一个重要优点，是多个程序可以共享同一份动态库代码。例如多个程序都使用 `libc.so.6` 时，系统只需要装入一份共享库代码页，这样更节省内存和磁盘空间。

静态链接则不同。每个静态链接程序都会包含一份自己的库函数实现副本，因此：

- 文件更大；
- 多个程序之间不能像共享库那样共享同一份库代码；
- 如果库升级或修复漏洞，静态链接程序通常需要重新链接才能获得更新。

而动态链接程序只要系统中的共享库被更新，很多情况下就可以直接受益，这也是动态链接在通用 Linux 环境中更常见的重要原因。

## 总结

静态链接与动态链接生成的可执行程序，在文件大小、内部结构、函数调用方式以及运行时依赖等方面都有明显差异。动态链接生成的程序较小，运行时依赖共享库，并通过 `PLT/GOT` 机制定位库函数；静态链接生成的程序较大，但把需要的库函数实现直接打包进自身，运行时更独立。就本实验而言，`main_sub_dyn` 只有约 `20K`，并依赖 `libc.so.6`；而 `main_sub_static` 达到约 `884K`，且不存在动态段。这些现象清楚地体现了两种链接方式在生成可执行程序时的本质区别。
