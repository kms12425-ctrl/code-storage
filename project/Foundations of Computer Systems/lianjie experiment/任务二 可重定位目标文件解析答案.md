# 任务二 可重定位目标文件解析答案


### 1.1 节头表各列含义

`readelf -S -W main.o` 输出表头如下：

```text
[Nr] Name Type Address Off Size ES Flg Lk Inf Al
```

各列含义如下：

- `Nr`：节编号。
- `Name`：节名，例如 `.text`、`.data`、`.bss`。
- `Type`：节类型。
  - `PROGBITS` 表示节中有实际内容，如代码、常量、已初始化数据。
  - `NOBITS` 表示该节在逻辑上存在，但在文件中不真正占字节，典型代表是 `.bss`。
  - `RELA` 表示重定位节。
  - `SYMTAB` 表示符号表节。
  - `STRTAB` 表示字符串表节。
- `Address`：节装入内存后的地址。对于 `main.o` 这样的可重定位目标文件，链接前地址通常还是 `0`。
- `Off`：该节在目标文件中的起始偏移。
- `Size`：该节大小。
- `ES`：每个表项的大小。普通节一般为 `0`，表结构节如符号表、重定位表通常非 `0`。
- `Flg`：节属性。
  - `W`：可写。
  - `A`：装入内存。
  - `X`：可执行。
  - `M`：可合并。
  - `S`：内容为字符串。
  - `I`：该节带有附加信息，常出现在重定位节中。
- `Lk`：该节关联的其他节编号。例如重定位节通常关联符号表。
- `Inf`：附加信息。对于重定位节，通常表示“该重定位节是给哪一个节服务的”。
- `Al`：地址对齐要求。

### 1.3 `main.o` 中的主要节及其作用

从输出结果可见，`main.o` 一共有 27 个节。结合本实验内容，其中最主要的节如下。

#### 1. 代码相关节

- `.text`

  这是代码节，存放函数对应的机器指令。对于本实验，它主要保存 [main.c](main.c#L23) 到 [main.c](main.c#L62) 中 `fcount`、`fsub`、`main` 编译后的指令。

- `.rela.text`

  这是 `.text` 的重定位节。由于目标文件生成时，某些符号地址还不能最终确定，例如调用 `printf`、`strcpy`、`fadd`，或访问某些全局变量地址，所以编译器先在代码中保留位置，链接时再根据 `.rela.text` 中的条目修正。

#### 2. 数据相关节

- `.data`

  这是已初始化全局变量和静态变量所在的节，保存了变量的实际初值。例如 [main.c](main.c#L10) 中的 `init_gv1 = 10`、[main.c](main.c#L12) 中的 `init_gstr1 = "U202490042"`、[main.c](main.c#L14) 中的 `init_garr1 = {11, 12, 13}`、[main.c](main.c#L20) 中的 `gv = NUMBER`。

- `.bss`

  这是未初始化全局变量和静态变量所在的节。例如 [main.c](main.c#L11) 中的 `uninit_gv2`、[main.c](main.c#L13) 中的 `uninit_gstr2`、[main.c](main.c#L15) 中的 `uninit_garr2`、[main.c](main.c#L18) 中的 `uninit_gp2`、[main.c](main.c#L19) 中的 `uninit_gfp2`。这类变量在文件中不需要存实际初值，因此 `.bss` 的类型是 `NOBITS`。

- `.data.rel.local`

  该节存放“已初始化，但初值中包含本目标文件内部符号地址”的数据。例如 [main.c](main.c#L16) 中的 `init_gp1 = &init_gv1` 和 [main.c](main.c#L17) 中的 `init_gp2 = &uninit_gv2`。它们虽然有初值，但这个初值本质上是地址，所以仍需重定位。

- `.rela.data.rel.local`

  这是 `.data.rel.local` 对应的重定位节。

- `.data.rel`

  该节存放“已初始化，但初值中包含外部符号地址”的数据。例如 [main.c](main.c#L19) 中的 `init_gfp1 = fadd`，其中 `fadd` 的定义在 [sub.c](sub.c#L8) 中，因此对 `main.o` 来说它是外部符号，链接前地址还不能确定。

- `.rela.data.rel`

  这是 `.data.rel` 对应的重定位节。

#### 3. 只读数据节

- `.rodata`

  这是只读数据节，主要存放字符串常量等只读内容。例如 [main.c](main.c#L29) 中 `printf` 的格式串、[main.c](main.c#L36) 中局部字符数组 `fmt` 初始化时使用的字符串常量、[main.c](main.c#L57) 和 [main.c](main.c#L61) 中 `printf` 使用的格式串等。

#### 4. 符号和字符串相关节

- `.symtab`

  这是符号表节，记录函数名、全局变量名、静态变量名、外部未定义符号名等，并保存符号的值、大小、绑定属性、所属节等信息。

- `.strtab`

  这是字符串表节，主要存放符号表中用到的名字字符串。符号表中的名称通常不是直接存文本，而是通过偏移索引到该节。

- `.shstrtab`

  这是节名字符串表，保存各节的名称，例如 `.text`、`.data`、`.bss` 等。

#### 5. 调试与辅助信息节

- `.debug_info`、`.debug_abbrev`、`.debug_aranges`、`.debug_line`、`.debug_str`、`.debug_line_str`

  这些是调试信息节。由于编译时使用了 `-g`，编译器会把源代码行号、变量、类型等调试信息保存在这些节中，以便 `gdb`、`readelf` 等工具分析。

- `.rela.debug_info`、`.rela.debug_aranges`、`.rela.debug_line`

  这些是对应调试节的重定位节。

- `.eh_frame`、`.rela.eh_frame`

  存放异常展开和栈回溯相关信息。

- `.comment`

  存放编译器版本等注释信息。

- `.note.GNU-stack`

  用于说明程序栈是否可执行。

- `.note.gnu.property`

  记录 GNU 平台相关属性。

### 1.4 总结

`main.o` 的节头表反映了可重定位目标文件的整体组织结构。就本实验而言，可以把它概括为以下几类：

- `.text`：存放代码。
- `.data`：存放已初始化的普通全局/静态数据。
- `.bss`：存放未初始化的全局/静态数据。
- `.rodata`：存放只读常量，尤其是字符串常量。
- `.rela.*`：存放重定位信息，说明哪些位置在链接时还需要修正。
- `.symtab`、`.strtab`、`.shstrtab`：用于保存符号和名称信息。
- `.debug_*`：用于调试。

因此，节头表不仅说明了 `main.o` 中“有哪些节”，也说明了这些节在编译、链接和调试过程中的具体作用。

## 2. 与全局变量及静态局部变量相关的节

### 2.1 `.data` 节的内容及其与初始化值的对应关系

实验命令：

```bash
readelf -x .data main.o
```

输出如下：

```text
Hex dump of section '.data':
  0x00000000 0a000000 00000000 55323032 34393030
  0x00000010 34320000 00000000 0b000000 0c000000
  0x00000020 0d000000 06000000
```

`.data` 节中存放的是已经初始化、并且初值可以直接写入目标文件的全局变量。结合 [main.c](main.c#L12) 到 [main.c](main.c#L24)，其对应关系如下：

- `0x00000000` 处的 `0a000000` 表示整数 `10`，对应 [main.c](main.c#L12) 中的 `int init_gv1 = 10;`。
- `0x00000008` 到 `0x00000013` 的内容 `55323032 34393030 34320000` 对应字符串 `U202490042\0\0`，即 [main.c](main.c#L14) 中的 `char init_gstr1[12] = "U202490042";`。
- `0x00000018` 开始的 `0b000000 0c000000 0d000000` 分别表示 `11`、`12`、`13`，对应 [main.c](main.c#L16) 中的 `int init_garr1[3] = {11, 12, 13};`。
- `0x00000024` 处的 `06000000` 表示整数 `6`，对应 [main.c](main.c#L24) 中的 `int gv = NUMBER;`，其中 `NUMBER=6`。

其中出现的 `00000000` 有两种作用：一部分是字符串结尾补 `0`，另一部分是编译器为了满足对齐要求加入的填充字节。

需要注意的是，[main.c](main.c#L18) 到 [main.c](main.c#L20) 中 `init_gp1`、`init_gp2`、`init_gfp1` 虽然也是已初始化全局变量，但它们的初值是地址，链接前还需要重定位，因此不放在普通 `.data` 节，而放在 `.data.rel.local` 或 `.data.rel` 中。

### 2.2 `.data` 节中定义了哪些符号，以及 Value 与位置的关系

实验命令：

```bash
readelf -s main.o | awk '$7==3 || NR==3'
```

输出中 `Ndx=3` 表示该符号定义在第 3 节，也就是 `.data` 节。可以看到 `.data` 中主要有以下符号：

- `init_gv1`，`Value=0`，`Size=4`
- `init_gstr1`，`Value=8`，`Size=12`
- `init_garr1`，`Value=24`，`Size=12`
- `gv`，`Value=36`，`Size=4`

这里的 `Value` 对于可重定位目标文件来说，不是最终虚拟地址，而是该符号在本节中的偏移量。因此：

- `init_gv1` 从 `.data` 偏移 `0x0` 开始。
- `init_gstr1` 从 `.data` 偏移 `0x8` 开始。
- `init_garr1` 从 `.data` 偏移 `0x18` 开始。
- `gv` 从 `.data` 偏移 `0x24` 开始。

这与前面 `.data` 的十六进制内容正好一一对应，说明符号表中的 `Value` 可以用来定位该符号在节中的具体位置。

### 2.3 `.bss` 节中包含哪些符号，以及为什么放在 `.bss`

实验命令：

```bash
readelf -s main.o | awk '$7==4 || NR==3'
```

其中 `Ndx=4` 表示符号定义在第 4 节，也就是 `.bss` 节。该节中主要包含：

- `count.0`
- `uninit_gv2`
- `uninit_gstr2`
- `uninit_garr2`
- `uninit_gp2`
- `uninit_gfp2`

其中，`uninit_gv2`、`uninit_gstr2`、`uninit_garr2`、`uninit_gp2`、`uninit_gfp2` 都是 [main.c](main.c#L13) 到 [main.c](main.c#L20) 中未显式初始化的全局变量；`count.0` 则对应 [main.c](main.c#L28) 中的静态局部变量 `static int count = 0;`。

它们之所以放在 `.bss` 节，是因为这些变量在目标文件中不需要保存实际初值，只需要记录大小并在装载时默认清零，因此使用 `.bss` 可以节省目标文件空间。

### 2.4 `.data.rel.local`、`.rela.data.rel.local`、`.data.rel`、`.rela.data.rel` 的内容及作用

实验命令：

```bash
readelf -x .data.rel.local main.o
readelf -r main.o
readelf -x .data.rel main.o
```

`.data.rel.local` 的内容是 16 字节的 `0`，`.data.rel` 的内容是 8 字节的 `0`。这些 `0` 只是占位，说明其中保存的是地址，但在目标文件阶段地址还没有最终确定。

对应的重定位节中可以看到：

- `.rela.data.rel.local` 有 2 个条目，分别对应 `init_gv1` 和 `uninit_gv2`。
- `.rela.data.rel` 有 1 个条目，对应 `fadd`。

这说明：

- `.data.rel.local` 中存放的是“已初始化，但初值引用了本文件内部符号地址”的全局变量，例如 [main.c](main.c#L18) 中的 `init_gp1 = &init_gv1;` 和 [main.c](main.c#L19) 中的 `init_gp2 = &uninit_gv2;`。
- `.rela.data.rel.local` 记录这些位置在链接时应该被修正为哪个内部符号地址。
- `.data.rel` 中存放的是“已初始化，但初值引用了外部符号地址”的全局变量，例如 [main.c](main.c#L21) 中的 `init_gfp1 = fadd;`。
- `.rela.data.rel` 记录这些位置在链接时应该被修正为哪个外部符号地址。

因此，这几类节主要服务于“初值中含有地址”的全局变量。

### 2.5 `.strtab` 中出现了哪些种类的名称

实验命令：

```bash
readelf -p .strtab main.o
```

`.strtab` 是字符串表，主要存放符号表中用到的名字字符串。该节中出现的名称不只是变量名，还包括多种类型的符号名称，例如：

- 全局变量名：`init_gv1`、`uninit_gv2`、`init_gstr1`、`init_garr1`、`gv`
- 函数名：`main`、`fcount`
- 外部符号名：`fadd`、`printf`、`strcpy`、`check_gcc_condition`、`extern_int`
- 静态局部符号名：`count.0`
- 源文件名：`main.c`

因此，`.strtab` 的作用是为 `.symtab` 中的各类符号提供名称字符串。

### 2.6 一个全局变量定义语句在可重定位目标文件中会生成哪些信息

一个全局变量定义语句在可重定位目标文件中，通常不只对应一个地方，而是会在多个节中留下信息。

如果是普通已初始化全局变量，例如 [main.c](main.c#L12) 中的 `int init_gv1 = 10;`，通常会：

- 在 `.data` 中保存变量初值。
- 在 `.symtab` 中生成该变量的符号表项。
- 在 `.strtab` 中保存变量名字符串。

如果是未初始化全局变量，例如 [main.c](main.c#L13) 中的 `int uninit_gv2;`，通常会：

- 在 `.bss` 中分配空间。
- 在 `.symtab` 中生成符号表项。
- 在 `.strtab` 中保存变量名。

如果是初值中含地址的全局变量，例如 [main.c](main.c#L18) 中的 `init_gp1 = &init_gv1;` 或 [main.c](main.c#L21) 中的 `init_gfp1 = fadd;`，则除了会在 `.data.rel.local` 或 `.data.rel` 中留出数据位置外，还会在对应的 `.rela.*` 重定位节中生成重定位条目，同时在 `.symtab` 和 `.strtab` 中记录相关符号信息。

因此，一个全局变量定义语句通常至少会在“数据节或 `.bss` 节、`.symtab`、`.strtab`”中留下信息；如果涉及地址初始化，还会额外产生重定位节信息。

## 3. 代码节及代码节的重定位节

### 3.1 `.text` 节和 `.rela.text` 节的内容及对应关系

实验命令：

```bash
readelf -x .text main.o
readelf -r main.o
```

其中，`readelf -S -W main.o` 可以看到 `.text` 是第 1 节，偏移为 `0x40`，大小为 `0x1fb` 字节；`.rela.text` 是专门为 `.text` 服务的重定位节。

`readelf -x .text main.o` 的部分输出如下：

```text
Hex dump of section '.text':
  0x00000000 f30f1efa 554889e5 4883ec10 c745fc00
  0x00000010 00000083 45fc018b 05000000 0083c001
  0x00000020 89050000 00008b15 00000000 8b45fc89
  0x00000030 c6488d05 00000000 4889c7b8 00000000
  0x00000040 e8000000 0090c9c3 554889e5 4881ecc0
```

这些十六进制内容本质上就是机器指令，对应 [main.c](main.c#L23) 到 [main.c](main.c#L63) 中几个函数编译后的代码，也就是：

- [main.c](main.c#L23) 到 [main.c](main.c#L30) 的 `fcount`
- [main.c](main.c#L32) 到 [main.c](main.c#L40) 的 `fsub`
- [main.c](main.c#L42) 到 [main.c](main.c#L63) 的 `main`

但 `.text` 中并不是所有位置在编译阶段都能直接确定最终值。凡是指令里涉及“地址”或“相对位移”的部分，例如：

- 访问全局变量
- 访问字符串常量
- 调用函数

编译器往往先在 `.text` 中留出占位字节，再在 `.rela.text` 中记录“将来该如何修正”。

`.rela.text` 的部分输出如下：

```text
Relocation section '.rela.text' at offset 0xf00 contains 29 entries:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
000000000019  000300000002 R_X86_64_PC32     0000000000000000 .bss + 34
000000000022  000300000002 R_X86_64_PC32     0000000000000000 .bss + 34
000000000028  000300000002 R_X86_64_PC32     0000000000000000 .bss + 34
000000000034  000400000002 R_X86_64_PC32     0000000000000000 .rodata - 4
000000000041  001a00000004 R_X86_64_PLT32    0000000000000000 printf - 4
...
000000000106  000e00000002 R_X86_64_PC32     0000000000000008 init_gstr1 - 4
00000000010e  001d00000004 R_X86_64_PLT32    0000000000000000 check_gcc_condition - 4
000000000118  001900000004 R_X86_64_PLT32    0000000000000000 fcount - 4
000000000122  001900000004 R_X86_64_PLT32    0000000000000000 fcount - 4
...
0000000001ac  001600000004 R_X86_64_PLT32    0000000000000000 fadd - 4
0000000001c8  001500000002 R_X86_64_PC32     0000000000000000 init_gfp1 - 4
0000000001f0  001a00000004 R_X86_64_PLT32    0000000000000000 printf - 4
```

从这个表可以看出，`.rela.text` 中每个重定位条目最核心的信息包括：

- `Offset`：需要修正的地点，也就是 `.text` 节内哪一个偏移位置上的指令字段需要在链接时被改写。
- `Type`：重定位类型，说明应该按什么规则计算并写回。
- `Sym. Name + Addend`：要参考哪个符号，以及附加常数是多少。

对于本实验，最常见的两类重定位是：

- `R_X86_64_PC32`

  这是基于程序计数器相对寻址的重定位，常见于访问全局变量或访问 `.rodata` 中的字符串常量。例如：

  - `000000000034 ... .rodata - 4` 表示 `.text` 偏移 `0x34` 处的指令要在链接时改成指向 `.rodata` 中相应字符串的位置，对应 [main.c](main.c#L29) 中 `printf` 使用的格式串。
  - `0000000000a4 ... uninit_gv2 - 4` 表示 `.text` 偏移 `0x0a4` 处的指令要根据全局变量 `uninit_gv2` 的地址来修正，对应 [main.c](main.c#L36) 到 [main.c](main.c#L37) 中对该变量地址和值的访问。
  - `000000000106 ... init_gstr1 - 4` 表示 `.text` 中调用 `check_gcc_condition` 前，需要先取到全局字符数组 `init_gstr1` 的地址，对应 [main.c](main.c#L44)。

- `R_X86_64_PLT32`

  这是与函数调用相关的重定位类型，常见于 `call` 指令。例如：

  - `000000000041 ... printf - 4` 对应 [main.c](main.c#L29) 中 `fcount` 内部对 `printf` 的调用。
  - `00000000010e ... check_gcc_condition - 4` 对应 [main.c](main.c#L44) 中 `main` 对 `check_gcc_condition` 的调用。
  - `000000000118 ... fcount - 4` 和 `000000000122 ... fcount - 4` 分别对应 [main.c](main.c#L45) 与 [main.c](main.c#L46) 中两次调用 `fcount`。
  - `0000000001ac ... fadd - 4` 对应 [main.c](main.c#L58) 中对外部函数 `fadd` 的调用。

把 `.text` 和 `.rela.text` 对照起来，可以把它们的关系概括为：

- `.text` 保存的是代码本体，即实际机器指令。
- `.rela.text` 保存的是这些机器指令中“哪些位置尚未最终确定”。
- 链接器在链接阶段根据 `.rela.text` 中的条目，到 `.text` 的指定偏移处回填正确的地址或相对位移。

因此，`.rela.text` 并不是单独存在的“另一份代码”，而是 `.text` 的修正说明书。它记录了代码中与符号地址有关的位置，以便把可重定位目标文件最终连接成可执行文件。

### 3.2 符号表中在 `.text` 节定义的符号

实验命令：

```bash
readelf -s main.o | awk 'NR<=3 || $7==1'
```

由于 `.text` 是第 1 节，因此 `Ndx=1` 表示符号定义在 `.text` 节中。输出如下：

```text
Symbol table '.symtab' contains 31 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     2: 0000000000000000     0 SECTION LOCAL  DEFAULT    1 .text
     6: 0000000000000048   175 FUNC    LOCAL  DEFAULT    1 fsub
    25: 0000000000000000    72 FUNC    GLOBAL DEFAULT    1 fcount
    28: 00000000000000f7   260 FUNC    GLOBAL DEFAULT    1 main
```

可以看到，符号表中定义在 `.text` 节里的符号主要有：

- `.text`

  这是一个 `SECTION` 类型的节符号，表示第 1 节本身。它不是源程序里写出的函数，而是符号表中用于表示代码节本身的一个条目。

- `fsub`

  这是 [main.c](main.c#L32) 到 [main.c](main.c#L40) 中定义的静态函数。它的 `Value=0x48`，表示该函数从 `.text` 节内偏移 `0x48` 的位置开始；`Type=FUNC` 表明它是函数符号；`Bind=LOCAL` 说明它只在本目标文件内部可见，这也与它被声明为 `static` 一致。

- `fcount`

  这是 [main.c](main.c#L23) 到 [main.c](main.c#L30) 中定义的全局函数。它的 `Value=0x0`，说明它位于 `.text` 的起始位置；`Size=72` 说明该函数占用了 72 字节代码；`Bind=GLOBAL` 说明它是全局可见符号。

- `main`

  这是 [main.c](main.c#L42) 到 [main.c](main.c#L63) 中定义的主函数。它的 `Value=0xf7`，表示该函数从 `.text` 节偏移 `0xf7` 处开始；`Size=260` 说明它对应 260 字节机器代码；`Bind=GLOBAL` 说明它也是全局符号。

这里的 `Value` 需要特别注意：对于 `main.o` 这样的可重定位目标文件，它并不是函数最终装入内存后的虚拟地址，而只是该符号在所属节中的偏移量。因此：

- `fcount` 位于 `.text + 0x0`
- `fsub` 位于 `.text + 0x48`
- `main` 位于 `.text + 0xf7`

这说明，符号表不仅告诉我们“有哪些函数定义在 `.text` 中”，也告诉我们“这些函数在代码节中的相对位置和大小”。

### 3.3 小结

对于可重定位目标文件来说，`.text` 与 `.rela.text` 是紧密配合的两类节：

- `.text` 保存函数编译后的机器指令。
- `.rela.text` 保存这些指令中需要在链接阶段进一步修正的位置和规则。
- `.symtab` 中 `Ndx=1` 的函数符号则说明了 `.text` 节里具体定义了哪些函数，以及它们在代码节中的偏移和大小。

因此，通过同时分析 `.text`、`.rela.text` 和 `.symtab`，就可以把“代码长什么样”“哪些地方还未最终确定”“这些代码分别对应哪个函数”三个问题联系起来理解。

## 4. 符号表节

### 4.1 符号表的内容及各列含义

实验命令：

```bash
readelf -s main.o
```

输出表头如下：

```text
Symbol table '.symtab' contains 31 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
```

其中各列含义如下：

- `Num`：符号表项编号，也就是该符号在符号表中的序号。

- `Value`：符号的值。

  对于 `main.o` 这样的可重定位目标文件来说，它通常不是最终装入内存后的地址，而是符号在所属节中的偏移量。例如定义在 `.text` 节中的函数，`Value` 表示该函数在 `.text` 节中的起始偏移；定义在 `.data` 或 `.bss` 中的变量，`Value` 表示该变量在对应节中的偏移。如果符号未定义，则 `Value` 往往为 `0`。

- `Size`：符号大小。

  对函数来说，表示该函数对应机器代码所占的字节数；对变量来说，表示对象占用的字节数；有些未定义符号或辅助符号的 `Size` 可能为 `0`。

- `Type`：符号类型。

  本实验中常见的类型包括：

  - `FUNC`：函数符号。
  - `OBJECT`：对象符号，一般是变量。
  - `SECTION`：节符号，表示某个节本身。
  - `FILE`：源文件符号，例如 `main.c`。
  - `NOTYPE`：没有进一步类型说明的符号，外部未定义符号常见为此类型。

- `Bind`：符号绑定属性，表示符号的可见范围。

  - `LOCAL`：局部符号，只在本目标文件内部可见。
  - `GLOBAL`：全局符号，可以被其他目标文件引用，或者引用其他文件中的同名全局符号。

- `Vis`：符号可见性。

  本实验中大多显示为 `DEFAULT`，表示默认可见性。

- `Ndx`：符号所属节编号。

  如果显示为具体数字，例如 `1`、`3`、`4`，表示该符号定义在对应编号的节中；如果显示为 `UND`，表示该符号在当前目标文件中只有引用而没有定义；如果显示为 `ABS`，表示该符号是绝对符号，不依附于普通节。

- `Name`：符号名称。

  可以是函数名、变量名、节名、源文件名等。

从本实验的符号表可以看出，`.symtab` 中既有本文件自己定义的符号，例如 [main.c](main.c#L23) 中的 `fcount`、[main.c](main.c#L32) 中的 `fsub`、[main.c](main.c#L42) 中的 `main`，也有只在本文件中被引用、要等链接阶段再解析的外部符号。

### 4.2 符号表中哪些符号是未定义的，以及为什么未定义

实验命令：

```bash
readelf -s main.o | awk 'NR<=3 || $7=="UND"'
nm -u main.o
```

输出如下：

```text
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     0: 0000000000000000     0 NOTYPE  LOCAL  DEFAULT  UND
    22: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND fadd
    26: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND printf
    27: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND __stack_chk_fail
    29: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND check_gcc_condition
    30: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND extern_int
```

其中，第 `0` 项是符号表的空表项，它是 ELF 符号表中的保留项，不表示用户程序里的一个实际未定义符号。除去这一保留项后，`main.o` 中真正未定义的符号主要有以下几个。

- `fadd`

  它在 [main.c](main.c#L7) 中只有函数声明，在 [main.c](main.c#L19) 中被赋给函数指针 `init_gfp1`，在 [main.c](main.c#L58) 中又被直接调用；但它的函数体并不在 `main.c` 中，而是在 [sub.c](sub.c#L8) 中定义。因此对 `main.o` 来说，它只是“被引用”，还没有“被定义”，所以在符号表中显示为 `UND`。

- `printf`

  它在 [main.c](main.c#L29)、[main.c](main.c#L38)、[main.c](main.c#L57)、[main.c](main.c#L61) 中被多次调用。`printf` 属于 C 标准库函数，并不由当前源文件定义，因此在 `main.o` 中它也是未定义符号，要等最终链接时由标准库提供定义。

- `__stack_chk_fail`

  这个符号不是程序员显式写出的函数，而是编译器在启用栈保护机制时自动引入的运行库函数。由于 [main.c](main.c#L35) 中存在局部字符数组 `fmt`，编译器会在函数中加入栈保护检查；一旦检查失败，就会调用 `__stack_chk_fail`。因此它也属于当前目标文件中只引用、不定义的外部符号。

- `check_gcc_condition`

  它在 [main.c](main.c#L8) 中只有声明，在 [main.c](main.c#L44) 中被调用；真正的定义在 [sub.c](sub.c#L19) 中。所以对于 `main.o` 来说，它同样是外部未定义符号，需要在链接阶段解析。

- `extern_int`

  它在 [main.c](main.c#L20) 中以 `extern` 形式声明，并在 [main.c](main.c#L56) 中被赋值；但真正的定义在 [sub.c](sub.c#L6) 中。因此 `main.o` 只记录了对该变量的引用，而没有给它分配定义性的存储空间，所以它在符号表中显示为未定义。

这些未定义符号之所以会出现在 `main.o` 中，主要有两类原因：

- 一类是符号定义在其他源文件中，而当前文件只是声明并使用它，例如 `fadd`、`check_gcc_condition`、`extern_int`。它们要等 `main.o` 与由 [sub.c](sub.c) 生成的目标文件一起链接时才能解析。
- 另一类是符号由标准库或编译器运行库提供，而不是由当前用户源码自己定义，例如 `printf` 和 `__stack_chk_fail`。它们会在最终生成可执行文件时由系统库补齐。

### 4.3 小结

`.symtab` 是分析可重定位目标文件时最重要的节之一。它不仅列出了当前目标文件中定义了哪些函数和变量，还通过 `Ndx` 一列区分了“已经在本文件中定义的符号”和“目前只有引用、需要链接阶段解析的未定义符号”。

因此，通过分析符号表，一方面可以看出程序中有哪些代码和数据实体，另一方面也可以看出该目标文件对其他目标文件或系统库存在哪些依赖关系。

## 5. 只读节

### 5.1 `.rodata` 中的内容，以及程序中哪些内容会放到 `.rodata` 节

实验命令：

```bash
readelf -x .rodata main.o
```

输出如下：

```text
Hex dump of section '.rodata':
  0x00000000 6175746f 2078203d 20256420 2c207374
  0x00000010 61746963 20636f75 6e74203d 25640a00
  0x00000020 64697370 6c617920 696e6974 5f677374
  0x00000030 7231203a 20257320 0a007375 6d203d20
  0x00000040 2564200a 00
```

把这些十六进制内容按 ASCII 还原后，可以看出 `.rodata` 中主要有以下字符串常量：

- `"auto x = %d , static count =%d\n"`

  对应 [main.c](main.c#L29) 中 `fcount` 里的 `printf` 格式串。

- `"display init_gstr1 : %s \n"`

  对应 [main.c](main.c#L57) 中 `main` 里的 `printf` 格式串。

- `"sum = %d \n"`

  对应 [main.c](main.c#L61) 中 `main` 里的 `printf` 格式串。

这说明，在本实验中，`.rodata` 节主要存放的是只读字符串常量，尤其是直接作为函数参数使用、运行期间不应被修改的格式串。

从程序角度看，通常会放入 `.rodata` 的内容主要包括：

- 字符串常量
- 其他只读常量数据
- 编译器决定以只读方式保存的常量对象

但需要注意的是，并不是程序中出现的所有“字符串”都会进入 `.rodata`。结合本程序，可以区分为以下几种情况：

- 直接作为只读字符串常量使用的内容，通常放在 `.rodata` 中。例如 [main.c](main.c#L29)、[main.c](main.c#L57)、[main.c](main.c#L61) 中 `printf` 的格式串。

- 全局已初始化字符数组，一般不放在 `.rodata`，而放在可写的数据节中。例如 [main.c](main.c#L12) 中的 `char init_gstr1[12] = "U202490042";`，因为它是可写的全局数组，所以放在 `.data` 而不是 `.rodata`。

- 局部字符数组初始化，也不一定以独立形式出现在 `.rodata` 中。例如 [main.c](main.c#L35) 中的 `char fmt[] = "static fsub : uninit_gv2 = %d \n";`。在当前 `main.o` 中，符号表里并没有名为 `fmt` 的独立只读符号，说明编译器没有把它单独作为一个可直接引用的 `.rodata` 符号保留下来，而是通过生成相应指令完成局部数组初始化。

因此，可以把这一问概括为：`.rodata` 节主要存放程序中的只读常量，本实验里最典型的是 `printf` 的格式串；而可写字符数组即使初值来自字符串字面量，也不一定进入 `.rodata`。

### 5.2 以 `printf` 调用为例，说明格式串首地址如何定位

实验命令：

```bash
objdump -dr main.o
readelf -r main.o
```

以 [main.c](main.c#L57) 中这条语句为例：

```c
printf("display init_gstr1 : %s \n", init_gstr1);
```

对应的关键反汇编片段如下：

```text
  18d: 48 8d 05 00 00 00 00    lea    0x0(%rip),%rax
                        18d: R_X86_64_PC32      .rodata + 1c
  191: 48 89 c7                mov    %rax,%rdi
  199: e8 00 00 00 00          call   19e <main+0xa7>
```

这里可以把格式串地址的定位过程分成 4 步来理解。

#### 1. 格式串本体先存放在 `.rodata` 中

上面第 5.1 节已经看到，字符串 `"display init_gstr1 : %s \n"` 存放在 `.rodata` 中，并且它的起始位置对应 `.rodata + 0x1c` 附近。

#### 2. `.text` 中先生成一条取地址指令

编译器在 `main` 的代码中生成了一条：

```text
lea 0x0(%rip), %rax
```

这条指令的作用是“根据当前指令指针 `RIP`，计算出某个目标地址”，这里目标地址就是格式串的首地址。

但是，在生成 `main.o` 这种可重定位目标文件时，`.rodata` 相对于这条指令的最终位置还不能完全确定，所以这里暂时只能写成占位的 `0x0`。

#### 3. `.rela.text` 中给出重定位说明

在 `.rela.text` 中，有与这条指令对应的重定位项：

```text
00000000018d  000400000002 R_X86_64_PC32     0000000000000000 .rodata + 1c
```

这条记录说明：

- `.text` 偏移 `0x18d` 处有一个需要修正的字段；
- 修正类型是 `R_X86_64_PC32`，也就是基于程序计数器的相对寻址；
- 它要指向的目标是 `.rodata + 0x1c`，也就是该格式串的首地址。

链接器在链接阶段会根据这条重定位记录，把 `lea` 指令里的占位值修正成正确的相对位移。

#### 4. 按调用约定把格式串地址传给 `printf`

格式串地址被 `lea` 算出后，先放入 `%rax`，随后通过：

```text
mov %rax, %rdi
```

复制到 `%rdi`。在 x86-64 的调用约定中，`printf` 的第一个参数正是通过 `%rdi` 传递的，所以这一步就把格式串首地址作为第一个实参交给了 `printf`。随后再执行 `call` 指令完成函数调用。

同样的过程也出现在 [main.c](main.c#L61) 和 [main.c](main.c#L29) 对 `printf` 的调用中。例如：

- `.text` 偏移 `0x34` 通过重定位 `R_X86_64_PC32 .rodata - 4` 指向 `fcount` 中使用的格式串。
- `.text` 偏移 `0x1e3` 通过重定位 `R_X86_64_PC32 .rodata + 36` 指向 `main` 中 `"sum = %d \n"` 对应的格式串。

因此，`printf` 格式串首地址的定位过程可以概括为：先把字符串常量保存在 `.rodata` 中，再在 `.text` 中生成一条基于 `RIP` 相对寻址的取地址指令，最后通过 `.rela.text` 的重定位条目在链接阶段把该指令修正正确，从而得到格式串的首地址。

### 5.3 小结

`.rodata` 是只读数据节，在本实验中主要保存了 `printf` 等函数使用的字符串常量。分析 `.rodata` 的内容可以帮助我们理解程序中哪些数据是只读的；而结合 `.text` 和 `.rela.text` 进一步分析，则可以看出这些只读字符串是如何在函数调用前被准确定位并传递给 `printf` 的。
