\subsection{实验概述}
\begin{enumerate}
  \item 熟练掌握程序开发平台(VS2019/VS2022/VS2023) 的基本用法，包括程序的编译、链接和调试；
  \item 熟悉数据的表示形式；
  \item 熟悉地址的计算方法、地址的内存转换；
  \item 用常见的按位操作（移位、按位与/或/非/异或）等实现运算表达式的等效运算。
\end{enumerate}

\subsection{实验内容}
任务1\quad 数据存放的压缩与解压编程

定义了 结构 student ，以及结构数组变量old\_s[N], new\_s[N];  (N=5)

\begin{lstlisting}[language=C]
struct student {
    char  name[8];
    short  age;
    float  score;
    char  remark[200];  // 备注信息
};
\end{lstlisting}

编写程序，输入N个学生的信息到结构数组old\_s中。将 old\_s[N] 中的所有信息依次紧凑(压缩)存放到一个字符数组message中，然后从 message 解压缩到结构数组 new\_s[N]中。打印压缩前(old\_s)、解压后(new\_s)的结果，以及压缩前、压缩后存放数据的长度。

要求：
\begin{enumerate}
  \item 输入的第0个人姓名(name)为自己的名字，分数为学号的最后两位；
  \item 编写指定接口的函数完成数据压缩
\end{enumerate}

压缩函数有两个：

\begin{lstlisting}[language=C]
int  pack_student_bytebybyte(student* s, int sno, char *buf);
int  pack_student_whole(student* s, int sno, char *buf);
\end{lstlisting}

s为待压缩数组的起始地址； sno 为压缩人数； buf 为压缩存储区的首地址；两个函数的返回均是调用函数压缩后的字节数。pack\_student\_bytebybyte要求一个字节一个字节的向buf中写数据；pack\_student\_whole要求对short、float字段都只能用一条语句整体写入，用strcpy实现串的写入。

\begin{enumerate}
  \setcounter{enumi}{2}
  \item 使用指定方式调用压缩函数
\end{enumerate}

old\_s数组的前N1（N1=2）个记录压缩调用pack\_student\_bytebybyte 完成；后N2（N2==3）个记录压缩调用pack\_student\_whole，两种压缩函数都只调用1次。

\begin{enumerate}
  \setcounter{enumi}{3}
  \item 使用指定的函数完成数据的解压
\end{enumerate}

解压函数的格式：

\begin{lstlisting}[language=C]
int restore_student(char *buf, int len, student* s);
\end{lstlisting}

buf 为压缩区域存储区的首地址；len为buf中存放数据的长度；s为存放解压数据的结构数组的起始地址； 返回解压的人数。解压时不允许使用函数接口之外的信息（即不允许定义其他全局变量）

\begin{enumerate}
  \setcounter{enumi}{4}
  \item 仿照调试时看到的内存数据，以十六进制的形式，输出message的前20个字节的内容，并与调试时在内存窗口观察到的message的前20个字节比较是否一致。
  \item 对于第0个学生的score，根据浮点数的编码规则指出其个部分的编码，并与观察到的内存表示比较，验证是否一致。
  \item 指出结构数组中个元素的存放规律，指出字符串数组、short类型的数、float型的数的存放规律。
\end{enumerate}

任务2\quad 编写位运算程序

按照要求完成给定的功能，并自动判断程序的运行结果是否正确。（从逻辑电路与门、或门、非门等等角度，实现CPU的常见功能。所谓自动判断，即用简单的方式实现指定功能，并判断两个函数的输出是否相同。）

\begin{enumerate}
  \item \texttt{int absVal(int x);}      返回 x 的绝对值

仅使用 !、 \textasciitilde{}、 \&、 \^{}、 |、 +、 <<、 >>， 运算次数不超过 10次

判断函数： \texttt{int absVal\_standard(int x)  \{ return (x < 0) ? -x : x;\}}

  \item \texttt{int negate(int x);}      不使用负号，实现 -x

判断函数： \texttt{int netgate\_standard(int x)  \{ return -x;\}}

  \item \texttt{int bitAnd(int x, int y);}  仅使用 \textasciitilde{} 和 |，实现 \&

判断函数： \texttt{int bitAnd\_standard(int x, int y)  \{ return x \& y;\}}

  \item \texttt{int bitOr(int x, int y);}    仅使用 \textasciitilde{} 和 \&，实现 |

  \item \texttt{int bitXor(int x, int y);}   仅使用 \textasciitilde{} 和 \&，实现 \^{}

  \item \texttt{int isTmax(int x);}    判断x是否为最大的正整数（7FFFFFFF），

只能使用 !、 \textasciitilde{}、 \&、 \^{}、 |、 +

  \item \texttt{int bitCount(int x);}   统计x的二进制表示中 1 的个数

                  只能使用，! \textasciitilde{} \& \^{} | + << >> ，运算次数不超过 40次

  \item \texttt{int bitMask(int highbit, int lowbit);} 产生从lowbit 到 highbit 全为1，其他位为0的数。例如bitMask(5,3) = 0x38 ；要求只使用 ! \textasciitilde{} \& \^{} | + << >> ；运算次数不超过 16次。

  \item \texttt{int addOK(int x, int y);}  当x+y 会产生溢出时返回1，否则返回 0

仅使用 !、 \textasciitilde{}、 \&、 \^{}、 |、 +、 <<、 >>， 运算次数不超过 20次

  \item \texttt{int byteSwap(int x, int n, int m);}  将x的第n个字节与第m个字节交换，返回交换后的结果。 n、m的取值在 0\textasciitilde{}3之间。

例：\texttt{byteSwap(0x12345678, 1, 3) = 0x56341278}

\phantom{例：}\texttt{byteSwap(0xDEADBEEF, 0, 2) = 0xDEEFBEAD}

仅使用 !、 \textasciitilde{}、 \&、 \^{}、 |、 +、 <<、 >>， 运算次数不超过 25次

  \item \texttt{int bang(int x)}    当 x =0 时，返回 1; 其他情况返回 0。实现逻辑非(!)

例：\texttt{bang(3) = 0；  bang(0) =1;}

仅使用 \textasciitilde{}、 \&、 \^{}、 | 、+、 <<、 >>，运算次数不超过 12次

提示：只有当 x=0时，x与 -x的最高二进制位会同时为0。

  \item \texttt{int bitParity(int x)}    当 x有奇数个二进制位0，返回1；否则返回0

例：\texttt{bitParity (5) = 0；  bitParity (7) = 1;}

仅使用 ! 、\textasciitilde{}、 \&、 \^{}、 | 、+ 、<< 、>>  ，运算次数不超过 20次。

提示：只有当 x的高字与低字的对应位（第0位对应第16位，第1位对应第17位，依次类推）同时为1，则出现了成对的二进制位1，此时，可以将对应的二进制位置为0，不会影响二进制位1的个数的奇偶性判断。
\end{enumerate}

\subsection{实验设计}

本实验的设计围绕“数据在内存中的真实表示”展开，分别从结构体紧凑存储和整数位级运算两个角度实现要求的功能。整体上，任务1强调对字节序、类型编码和结构体对齐的理解，任务2强调仅利用基本逻辑门等价规则构造常见运算。

\subsubsection{任务1设计思路}
任务1采用“按字段顺序串行化，再按相同顺序反串行化”的方案。原始结构体中各字段依次为 name、age、score、remark，其中 name 和 remark 为字符串，age 为 short，score 为 float。若直接存储结构体数组，每个元素会受到字节对齐影响，除有效字段外还会包含填充字节；而压缩后的 message 仅保留实际有用的数据，因此需要将每个学生记录拆解为可连续写入的字节序列。

具体实现时，将前两个学生记录交由 \texttt{pack\_student\_bytebybyte} 处理。该函数逐字节写入 name 和 remark 的字符内容，并显式补写字符串结束符 \texttt{'\\0'}；对于 age 和 score，则先取字段地址，再按底层字节表示逐个写入缓冲区。这样设计的目的是直接观察 short 与 float 在内存中的真实字节序，同时满足“逐字节压缩”的题目要求。

后 3 个学生记录交由 \texttt{pack\_student\_whole} 处理。该函数对字符串字段使用 \texttt{strcpy} 一次性复制，对 \texttt{short} 和 \texttt{float} 字段使用强制类型转换后整体写入，从而体现“按整体对象写入”的另一种压缩方式。两个压缩函数均返回本次写入的总字节数，主程序将两段长度相加即可得到 message 中有效数据的总长度。

解压部分由 \texttt{restore\_student} 完成。该函数维护当前读取位置 \texttt{cur\_len}，并严格按照“字符串、short、float、字符串”的顺序恢复一个学生记录。由于压缩时每个字符串都保留了结束符，因此解压时可以借助 \texttt{strcpy} 和 \texttt{strlen} 自动确定字符串长度；而 age 与 score 的读取则直接依据各自字节数推进偏移量。该方法不依赖额外全局信息，只依赖缓冲区首地址和有效长度，满足题目对函数接口的限制。

从数据组织角度看，该设计等价于将结构体数组重新编码为变长记录序列：字符串采用“字符流 + 结束符”存储，数值类型采用机器中的补码或 IEEE 754 单精度浮点编码直接存储。这样既能够比较压缩前后长度差异，也便于结合调试器内存窗口分析小端机器上的字节排列规律。

\subsubsection{任务2设计思路}
任务2的总体策略是将目标函数全部转换为补码运算、逻辑恒等变换和掩码操作，不使用题目限制之外的高级运算。为验证实现正确性，程序对每个自定义函数都编写了一个标准判定版本，并利用随机数据自动对拍；一旦出现不一致，立即输出失败信息并终止，从而保证测试过程具有可重复的判错能力。

在具体方法上，各类函数采用了不同但统一的位级构造思路。\texttt{absVal} 和 \texttt{negate} 依赖补码表示完成符号翻转与取反加一；\texttt{bitAnd}、\texttt{bitOr}、\texttt{bitXor} 基于德摩根律和逻辑等价式，用受限操作组合出目标逻辑；\texttt{isTmax}、\texttt{addOK}、\texttt{bang} 则通过符号位分析和特殊值判定来识别边界情况。这样的设计体现了“高级判断最终都可以归结为对符号位和进位关系的分析”。

对于较复杂的位操作，程序采用分治和掩码分层统计的思想。\texttt{bitCount} 依次构造 \texttt{0x55555555}、\texttt{0x33333333}、\texttt{0x0F0F0F0F} 等掩码，将 32 位整数中的局部计数逐步合并，最终得到全部 1 的个数；\texttt{bitMask} 通过构造上下边界掩码并组合，生成指定区间为 1 的结果；\texttt{byteSwap} 先提取第 \texttt{n}、\texttt{m} 个字节，再清空原位置并回填，实现字节级交换；\texttt{bitParity} 则不断将高位信息折叠到低位，通过异或累计奇偶性。上述方法避免了循环逐位判断，在操作次数受限的前提下更容易满足题目要求。

因此，实验1的设计重点并不只是“写出程序”，而是在实现过程中把结构体布局、字节序、浮点编码、补码表示和布尔代数这些底层原理转化为可执行的代码步骤，并通过自动测试与内存观察相互印证结果的正确性。

\subsubsection{具体实施步骤}
\begin{enumerate}

  \item 完成任务1的压缩与解压逻辑。程序首先固定第 0 个学生信息为 \texttt{Rocky, 20, 42.0, Great}，再从控制台输入其余 4 个学生数据。随后先输出压缩前的原始结构体数组，再调用 \texttt{pack\_student\_bytebybyte} 压缩前 2 个学生、调用 \texttt{pack\_student\_whole} 压缩后 3 个学生，并将两段结果顺序写入字符数组 \texttt{message}。
  \item 在完成压缩后，输出 \texttt{message} 前 40 个字节的十六进制内容，并在调试器中于压缩结束位置设置断点，打开内存窗口观察同一地址处的字节序列，比较控制台输出与内存窗口显示是否一致。同时根据 \texttt{score=42.0} 的 IEEE 754 单精度编码分析符号位、阶码和尾数，与实际内存表示进行核对。
  \item 调用 \texttt{restore\_student} 对 \texttt{message} 中的数据进行反串行化，重新生成结构数组 \texttt{decompress}，再将解压后的 5 条学生记录逐项打印，与压缩前数据进行人工比对，确认姓名、年龄、成绩和备注均保持一致。
  \item 完成任务2的 12 个位运算函数实现。对每一个目标函数，都编写一个使用普通 C/C++ 运算规则的标准版本，然后在 \texttt{main} 函数中采用随机数测试或边界值测试的方式自动对拍；若发现结果不一致，程序立即输出失败信息并终止，否则输出“测试通过”。
  \item 对 \texttt{isTmax}、\texttt{bang}、\texttt{bitMask}、\texttt{byteSwap} 和 \texttt{bitParity} 等容易受边界影响的函数进行重点检查。其中 \texttt{isTmax} 额外测试 \texttt{0x7FFFFFFF} 与 \texttt{-1}，\texttt{bang} 额外测试 \texttt{0}，\texttt{bitMask} 保证生成的随机区间满足 \texttt{low <= high}，从而避免因非法输入影响验证结果。
\end{enumerate}

\begin{lstlisting}[language=C, caption={任务1解压核心代码}, label={lst:restore-code}]
int restore_student(char *buf, int len, student *s)
{
    int cur_len = 0, i;
    for (i = 0; cur_len <= len; i++)
    {
        strcpy(s[i].name, buf + cur_len);
        cur_len = cur_len + strlen(s[i].name) + 1;

        s[i].age = *(short *)(buf + cur_len);
        cur_len = cur_len + sizeof(short);

        s[i].score = *(float *)(buf + cur_len);
        cur_len = cur_len + sizeof(float);

        strcpy(s[i].remark, buf + cur_len);
        cur_len = cur_len + strlen(s[i].remark) + 1;
    }
    return i + 1;
}
\end{lstlisting}

\subsection{实验内容}
任务1\quad 用C语言编写一个学生成绩管理程序，具有平均成绩计算、按平均成绩从高到低排序、显示学生成绩的功能

定义了结构 student，设有 N 个学生

struct student {

  \item 对于函数“计算平均成绩”、“按平均成绩从高到低排序”分别计时，显示两个函数的时间开销；
  \item 显示排序前、排序后的学生信息（姓名、学号、8门课的分数、平均分），一个学生一行。
  \item 对“计算平均成绩”、“按平均成绩排序”函数的Debug版、Release版的运行效率进行对比，比较两个版本下的反汇编代码的差异，分析程序执行速度提高的原因。

任务2\quad 用汇编语言编写函数“计算平均成绩”，代替原来用C语言编写的函数

任务3\quad 对用汇编语言编写的“计算平均成绩”函数进行优化

任务4\quad 对排序函数进行算法优化

\subsection{实验设计}
\subsubsection{解题思路分析}
实验2围绕“用汇编语言替换并优化关键计算路径”展开，整体程序由 C 主控逻辑和 MASM 编写的平均分计算函数两部分组成。首先使用 C 语言完成学生信息初始化、成绩显示、排序与计时框架，使程序具备完整的数据流和可观测输出；随后将“计算平均成绩”这一热点函数从 C 迁移到汇编语言实现，并进一步针对固定 8 门课这一已知条件做展开优化，以比较不同实现方式对运行效率的影响。

从功能分解上看，任务1负责构造完整的学生成绩管理流程，任务2将平均分计算改写为汇编版本，任务3在汇编版本基础上继续减少循环控制和除法开销，任务4则将按平均分排序交给标准库 \texttt{qsort} 完成，避免手写低效排序。这样设计的原因在于：平均分计算属于规则固定、重复次数高、适合底层优化的数值处理任务，而排序则更适合复用库中成熟实现，两者分别对应“指令级优化”和“算法级优化”两条路线。

因此，本实验并不是单纯把 C 代码翻译成汇编代码，而是将程序拆分为“高层流程由 C 管理、性能关键段由汇编实现”的协同结构，再结合计时结果分析不同层次优化带来的收益。这种分层设计既保留了程序的可读性，又能直接观察机器级实现对执行效率的影响。

\subsubsection{技术与方法}
实验所采用的数据结构为 \texttt{student} 结构体，每个学生包含姓名、学号、8 门课程分数和平均分字段。程序以结构体数组作为核心存储载体，先批量初始化，再依次执行平均分计算、排序和显示。由于 \texttt{scores} 为定长数组，汇编代码可以直接依据结构体偏移访问每一门成绩，从而避免额外的间接寻址开销。

在计时方法上，程序同时给出了 \texttt{QueryPerformanceCounter} 和 \texttt{GetTickCount} 的示例。正式计时统一由宏 \texttt{Time\_Anyfunc} 封装，并通过高精度性能计数器统计函数执行时间。相比 \texttt{GetTickCount}，这种方式更适合测量微小时间差，也更容易反映未优化版本与优化版本在平均分计算上的差异。

在汇编实现上，\texttt{computeAverageScore} 采用双层循环：外层遍历学生，内层遍历 8 门课程成绩并累加，最后通过 \texttt{idiv 8} 求出平均值。优化版 \texttt{computeAverageScore\_improve} 利用课程数固定这一条件，直接展开 8 次取数与累加操作，并将除以 8 替换为右移 3 位，从而减少循环分支、索引维护和除法指令的开销。排序部分使用 \texttt{qsort} 配合比较函数按平均分降序排列，体现以现成高效算法替代基础实现的优化思路。

    mov edi, sptr

student_loop:

    movzx edx, word ptr [edi].student.scores[0]

    add edi, type student
    dec ecx
    jnz student_loop
    ret

在平均分计算部分，未优化版本耗时约为 \texttt{0.000400 ms}，优化版本耗时约为 \texttt{0.000200 ms}，优化后时间约下降 50\%。这一结果与代码结构高度一致：未优化版本使用了课程循环和 \texttt{idiv} 指令，存在更多分支控制与整数除法开销；优化版本将 8 次取数完全展开，并把除以 8 转化为右移 3 位，因此指令路径更短、流水线更稳定。虽然绝对时间很短，但相对差异已经能够体现汇编级展开和位移优化的效果。

排序部分耗时约为 \texttt{0.017900 ms}，明显高于单次平均分计算，这是因为 \texttt{qsort} 需要多次比较与交换整个结构体记录。尽管如此，排序结果从 85 分一直降到 32 分，说明比较函数 \texttt{return s2->average - s1->average;} 能够正确实现降序逻辑。结合输出截图可以看到，排序前后学生的课程分数没有发生改变，仅记录顺序发生调整，说明排序操作保持了数据项的完整性。

对于 Debug 与 Release 的差异，当前工程文件表明 Release 的配置会减少额外调试检查、改善函数内联和链接期优化效果。因此在相同代码下，Release 版本理论上会比 Debug 版本具有更低的调用开销和更紧凑的目标代码。再叠加实验中手工编写的汇编优化，最终性能提升并不只来自汇编本身，也来自编译配置对整个程序执行路径的优化。

\subsection{实验设计}
\subsubsection{解题思路分析}
实验3的核心任务不是修改源程序，而是在缺失 \texttt{phases.c} 源代码的情况下，仅依据 \texttt{phases.o}、可执行程序行为以及反汇编结果恢复 6 个关卡的输入约束。为此，本实验采用“先建立可执行程序，再结合静态分析和动态调试逐关提取约束”的方案。整体上，先使用 \texttt{bomb.c}、\texttt{support.c} 与 \texttt{phases.o} 重新链接出可执行程序 \texttt{bomb}，再借助 \texttt{gdb} 观察关键比较点处的寄存器、栈变量和跳转目标，同时配合 \texttt{objdump} 和数据段内容恢复隐藏常量表与链表结构，最终得到全部通关答案。

之所以采用这种方案，是因为不同关卡对应的控制逻辑并不相同。第一关本质上是固定字符串比较，可以直接通过反汇编和只读数据段定位目标串。第二关和第三关与学号有关，适合在 \texttt{cmp} 指令前读取程序期望值，逐步修正输入。第四关需要理解递归函数 \texttt{func4} 的返回值编码规则，属于“先读取目标值，再反推出输入”的类型。第五关依赖字符低 4 位映射表，静态查看 \texttt{array.0} 与目标串即可构造答案。第六关则要从数据段恢复链表节点值，再按降序重新排列节点编号。换言之，本实验不是简单“猜答案”，而是针对每一关的机器级结构选择最合适的逆向路径。

因此，实验3的总体设计强调两点：一是把程序执行过程拆解为“输入读取、约束计算、最终比较”三个阶段，逐步定位答案来源；二是根据关卡特征在动态调试和静态推导之间切换，避免陷入纯暴力试错。这样既能提高拆弹效率，也能更直接地对应课程中关于控制流、数据流和目标代码结构的知识点。

\subsubsection{技术与方法}
实验中主要使用的技术手段包括 \texttt{gdb} 单步调试、\texttt{objdump} 反汇编、\texttt{nm} 符号查看和数据段静态分析。\texttt{gdb} 主要用于在关键比较指令或函数入口处设置断点，观察寄存器和栈上输入变量的内容，从而直接读出程序内部计算得到的期望值。\texttt{objdump -drwC} 用于恢复各关卡的完整控制流。\texttt{objdump -s -j .rodata} 和 \texttt{objdump -s -j .data} 用于提取固定字符串、字符映射表与链表节点值。\texttt{nm -n} 则辅助定位函数和数据符号。

从关卡结构上看，六关分别对应不同类型的机器级约束。第一关使用 \texttt{strings\_not\_equal} 比较输入串与固定常量。第二关读取 6 个整数，并检查前两项是否等于学号中指定字符的数字值、后四项是否满足递推关系。第三关先比较第 1 个整数是否等于学号某一位数字，再经由跳转表为第 2 个整数生成目标常量。第四关调用递归函数 \texttt{func4} 对搜索路径进行编码，并要求两个输入同时匹配目标值 \texttt{7}。第五关使用字符低 4 位作为下标访问数组 \texttt{array.0}，再将映射结果与字符串 \texttt{bruins} 比较。第六关则把 6 个整数解释为链表节点位置，按输入顺序重连链表，并要求新链表中节点值单调不增。

在数据结构方面，实验3涉及两个最关键的静态对象。其一是第五关中的字符映射表 \texttt{"maduiersnfotvbyl"}，它决定了输入字符经低 4 位映射后得到的输出串；其二是第六关中的 \texttt{listNode} 链表结构，节点中包含数值、编号和下一节点指针，只有将节点值按降序排列后，重新连接得到的节点序号序列才能通过最终比较。通过这些对象可以看出，二进制程序的输入校验本质上仍然依赖常量表、控制流分支和内存中的结构化数据，只是这些信息需要从机器级表示中恢复出来。

\subsubsection{结果分析}
实验3的结果表明，六个关卡的输入并不是彼此独立的“谜语”，而是分别对应六类常见的机器级程序结构。第一关是最直接的固定字符串比较；第二关引入了基于学号字符的参数化递推关系；第三关体现了 \texttt{switch/jump-table} 结构在汇编层的实现形式；第四关展示了递归函数如何把搜索路径编码到返回值中；第五关说明字符映射问题常常隐藏在数组索引和掩码运算里；第六关则把链表重连与顺序检查结合起来，要求同时理解数据结构和控制流。这些关卡覆盖了字符串、整数、分支、递归、表驱动和链表等多个层面的程序行为，因此非常适合作为机器级语言理解训练。

从求解过程看，动态调试和静态分析各有优势。第二关和第三关中，利用 \texttt{gdb} 在 \texttt{cmp} 指令前直接读取期望值，可以迅速确认学号相关的目标数字；而第五关和第六关若仅靠单步调试会比较繁琐，直接查看 \texttt{.rodata} 和 \texttt{.data} 中的映射表、目标串和节点值反而更高效。这说明在逆向分析中，正确选择分析入口比盲目增加断点更重要。只有把“控制流恢复”和“数据对象恢复”结合起来，才能真正高效地还原程序逻辑。

此外，实验结果也说明二进制程序虽然缺少高级语言源代码，但其语义并没有消失，而是被编码进了指令序列、常量表和内存布局中。例如第二关的递推式、第四关的 \texttt{func4}、第五关的映射数组以及第六关的链表节点值，都可以在汇编和数据段中被明确定位。也正因为如此，最终能够在不拥有 \texttt{phases.c} 的前提下完整推导出所有关卡答案，并通过截图验证全部通关。

\experimentsection{实验4：缓冲区溢出攻击}
\subsection{实验概述}
本实验围绕课程提供的缓冲区炸弹程序 \texttt{bufbomb} 展开，目标是在不修改源程序逻辑的前提下，仅通过构造输入字节串改变 \texttt{getbuf} 的返回行为。实验重点不在于“猜测字符串”，而在于结合函数调用约定、栈帧布局、小端序存储和控制流转移过程，分析缓冲区溢出为什么能够发生、攻击载荷应当如何组织，以及不同攻击目标对栈数据伪造程度的要求有何区别。

实验环境采用 Ubuntu、GCC 和 GDB。编译时关闭栈保护与位置无关执行，并根据本人学号 \texttt{U202490042} 的最后一位选择宏 \texttt{-DU2}，以保证 \texttt{getbuf} 的局部变量布局与调试分析一致。实验中主要使用 \texttt{gdb} 观察 \texttt{buf}、\texttt{rbp}、返回地址和目标函数入口地址，使用十六进制输入文件组织攻击载荷，再通过程序输出验证攻击是否成功。

\subsection{实验内容}
本次实验的总体内容是利用 \texttt{getbuf} 中对固定长度缓冲区 \texttt{buf} 的无边界复制漏洞，构造十六进制攻击串覆盖栈上的关键控制数据，从而改变函数返回后的执行路径。根据任务难度，实验分为两个阶段：第一阶段 smoke 仅要求覆盖返回地址并跳转到目标函数；第二阶段 fizz 不仅要劫持控制流，还要让目标函数读到正确参数，因此需要进一步伪造栈帧中的局部数据布局。

\begin{lstlisting}[language=C, caption={缓冲区溢出漏洞对应的关键代码}, label={lst:lab4-getbuf}]
int getbuf(char *src, int len)
{
  char buf[NORMAL_BUFFER_SIZE];
  Gets(buf, src, len);
  return 1;
}
\end{lstlisting}

\subsubsection{阶段1：smoke 返回地址覆盖攻击}
\noindent\textbf{1.任务描述：}本阶段要求在 \texttt{getbuf} 执行 \texttt{ret} 时，不返回 \texttt{test} 中原调用点，而是直接跳转到 \texttt{smoke} 函数入口，从而输出 \texttt{Smoke!: You called smoke()}。其本质是覆盖保存的返回地址，使其变为 \texttt{smoke} 的入口地址。

\noindent\textbf{2.实验设计：}该阶段只涉及最基本的控制流劫持，因此总体思路是先在 \texttt{getbuf} 建立栈帧后测量 \texttt{buf} 起始地址到保存返回地址的真实偏移，再查询 \texttt{smoke} 的入口地址，并将目标地址按 x86\_64 小端序写入攻击串尾部。由于 \texttt{buf} 的名义长度虽然为 32 字节，但在 \texttt{-DU2} 条件下，函数内还存在额外局部数组和编译器对齐空间，所以必须通过调试而不是经验估计来确认偏移量。

\noindent\textbf{3.实验过程：}首先使用以下命令重新编译程序，关闭栈保护并固定代码地址：

\begin{lstlisting}[language=Shell, caption={阶段1使用的编译与调试命令}, label={lst:lab4-smoke-cmd}]
gcc -g -fno-stack-protector -no-pie -DU2 -fcf-protection=none -z execstack \
  verinfo.c bufbomb.c buf.c -o bufbomb

gdb ./bufbomb
(gdb) b getbuf
(gdb) run U202490042 smoke_hex.txt 0
\end{lstlisting}

在 \texttt{getbuf} 入口停下后，先单步越过函数序言，再查看 \texttt{buf} 与返回地址位置。本次调试得到返回地址距 \texttt{buf} 起始地址的偏移为 88 字节，\texttt{smoke} 的入口地址为 \texttt{0x401445}。因此攻击串的前 88 个字节全部用 \texttt{0x41} 填充，最后 8 个字节写入 \texttt{smoke} 地址的小端序 \texttt{45 14 40 00 00 00 00 00}。最终攻击文件内容如下：

\begin{lstlisting}[language={}, caption={阶段1最终攻击串 smoke\_hex.txt}, label={lst:lab4-smoke-payload}]
41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 45 14 40 00 00 00 00 00
\end{lstlisting}

最后使用 \texttt{./bufbomb U202490042 smoke\_hex.txt 0} 运行程序，观察是否转入 \texttt{smoke}。

\noindent\textbf{4.实验结果：}程序成功输出 \texttt{Smoke!: You called smoke()}，说明返回地址已经被精确改写，\texttt{ret} 指令取出的不再是原返回点，而是 \texttt{smoke} 的入口地址。该结果表明：只要攻击者能够覆盖保存的返回地址，即使不修改任何源代码，也能直接改变程序控制流。这一阶段验证了缓冲区溢出的最基本破坏方式，即“覆盖返回地址并劫持执行路径”。

\subsubsection{阶段2：fizz 伪造栈帧攻击}
\noindent\textbf{1.任务描述：}本阶段要求 \texttt{getbuf} 返回后进入 \texttt{fizz} 的成功路径，并正确打印 \texttt{cookie} 值。与 smoke 不同，\texttt{fizz} 会比较参数 \texttt{val} 与全局变量 \texttt{cookie} 是否相等，因此仅把返回地址改成 \texttt{fizz} 入口并不能通过检查，必须让 \texttt{fizz} 在执行比较时读到正确的值。

\noindent\textbf{2.实验设计：}在 x86\_64 调用约定下，\texttt{fizz} 的第一个参数通过 \texttt{edi} 传递，函数入口还会执行参数落栈操作。如果直接跳到函数开头，寄存器中的参数无法由当前攻击串可靠控制。因此本阶段采用“跳过参数落栈指令 + 伪造 \texttt{rbp} + 在栈上预埋 \texttt{cookie}”的方案：让 \texttt{getbuf} 返回到 \texttt{fizz} 内部地址 \texttt{0x40146d}，避开用 \texttt{edi} 覆盖局部变量的语句；同时把保存的 \texttt{rbp} 改写成伪造值，使 \texttt{fizz} 随后访问 \texttt{[rbp-0x4]} 时，恰好读到攻击串中预先写入的 \texttt{cookie}。

\noindent\textbf{3.实验过程：}先在 \texttt{gdb} 中反汇编 \texttt{fizz}，确认入口地址为 \texttt{0x401462}，内部合适的落点地址为 \texttt{0x40146d}。然后继续在 \texttt{getbuf} 中测量栈布局。实验中测得 \texttt{buf} 起始地址为 \texttt{0x7fffffffce10}，保存的 \texttt{rbp} 距 \texttt{buf} 偏移 80 字节，返回地址距 \texttt{buf} 偏移 88 字节。为了让 \texttt{fizz} 访问 \texttt{[rbp-0x4]} 时读到正确值，将伪造的 \texttt{rbp} 设为 \texttt{0x7fffffffce60}，于是 \texttt{cookie} 应写在偏移 76 至 79 字节处。程序运行时打印的 \texttt{cookie} 为 \texttt{0x0c11c0ba}，其小端序字节为 \texttt{ba c0 11 0c}。最终攻击串由 76 个填充字节、4 字节 \texttt{cookie}、8 字节伪造 \texttt{rbp} 和 8 字节返回地址组成：

\begin{lstlisting}[language={}, caption={阶段2最终攻击串 fizz\_probe.txt}, label={lst:lab4-fizz-payload}]
41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 41 41 41 41 41 41 41 41
41 41 41 41 41 41 41 41 41 41 41 41 ba c0 11 0c
60 ce ff ff ff 7f 00 00 6d 14 40 00 00 00 00 00
\end{lstlisting}

由于该解法依赖稳定的栈地址，验证时需要关闭地址随机化，例如使用 \texttt{setarch \$(uname -m) -R ./bufbomb U202490042 fizz\_probe.txt 1}，或在 \texttt{gdb} 中开启 \texttt{set disable-randomization on} 后运行。

\noindent\textbf{4.实验结果：}程序成功输出 \texttt{Fizz!: You called fizz(0xc11c0ba)}，说明控制流已从 \texttt{getbuf} 正确转入 \texttt{fizz} 内部比较逻辑，且 \texttt{fizz} 读取到的 \texttt{val} 与 \texttt{cookie} 完全一致。与阶段1相比，本阶段不再只是单纯改写返回地址，而是进一步利用溢出伪造了新的栈帧语义，使目标函数把攻击者布置的数据当作合法局部变量读取。这说明缓冲区溢出不仅能改变跳转目标，还能联动破坏函数上下文和参数语义，其危害明显高于最简单的返回地址覆盖。

\subsection{实验小结}
本次实验以 \texttt{bufbomb} 为对象，完成了 smoke 与 fizz 两个阶段的缓冲区溢出攻击练习。在第一阶段中，我亲眼看到，只要将保存的返回地址悄悄替换掉，程序就会乖乖跳到我们指定的地方去执行；第二阶段则更进一步，不仅要骗过程序的执行路径，还要让目标函数误以为自己收到了"合法"的参数，这让我深刻感受到缓冲区溢出的威力远不止于让程序崩溃那么简单。

回顾整个实验过程，我发现自己用到了许多课上学过的知识：函数调用时的栈帧结构、小端序的字节存储方式、\texttt{gdb} 的断点调试，还有反汇编代码的阅读方法。以前这些知识在我眼里不过是一些孤立的概念，而这次实验把它们串联在了一起。测量 \texttt{buf} 与返回地址之间的偏移、找到 \texttt{smoke} 和 \texttt{fizz} 的入口地址、把 \texttt{cookie} 藏进精心构造的输入文件……每一步都让我更真切地体会到：数据和代码在内存里本质上没有区别，程序信任什么，攻击者就能伪造什么。

通过这次实验，我有三点收获让我印象深刻。第一，栈帧不再是课本上的示意图，而是真实存在于内存某个地址处的字节序列，我可以用调试器直接看到它、修改它。第二，攻击并不神秘，它不过是把程序自己的运行规则用在了出乎意料的地方。第三，也是最重要的一点，安全问题的根源往往不是技术有多复杂，而是程序员在写代码时忽略了"用户输入不可信"这一基本原则。如果后续还有机会，我很想继续完成 \texttt{bang} 和 \texttt{boom} 阶段，亲自验证一下开启栈保护和地址随机化之后攻击为什么会失效，把"怎么攻"和"怎么防"这两件事放在一起对比着理解。

\subsubsection{阶段1：从 C 程序到汇编语言程序}
\noindent\textbf{1.任务描述：}本阶段要求使用 \texttt{gcc -S -fverbose-asm -D U2 main.c -o main.s} 生成汇编文件，并结合具体变量与具体语句，分析全局变量、局部变量和函数调用在汇编程序中的表示形式，说明为什么有些对象进入 \texttt{.data} 段，有些对象进入 \texttt{.bss} 或 \texttt{.rodata} 段。

\noindent\textbf{2.实验设计：}这一阶段的重点是建立“高级语言语义”和“汇编层组织形式”之间的一一对应关系。实验选择三个最有代表性的切入点：一是比较 \texttt{init\_gstr1} 与 \texttt{uninit\_gstr2}，观察已初始化和未初始化全局变量分别如何进入 \texttt{.data} 与 \texttt{.bss}；二是用 \texttt{fadd(init\_gv1, lv1)}、\texttt{fsub(50,30)} 等调用语句说明参数寄存器、返回值寄存器和 \texttt{call} 指令的配合；三是比较全局变量通过 \texttt{symbol(\%rip)} 访问、局部变量通过 \texttt{offset(\%rbp)} 访问的差异，从而解释不同存储期对象在汇编层的定位方式。

\noindent\textbf{3.实验过程：}实验首先在 \texttt{lianjie experiment/main.c} 中将学号字符串改为 \texttt{U202490042}，并把内联汇编的重复次数调整为 2。随后执行 \texttt{gcc -S -fverbose-asm -D U2 main.c -o main.s} 生成 \texttt{lianjie experiment/main.s}。在分析过程中重点观察以下几类典型片段：一是 \texttt{init\_gstr1}、\texttt{init\_gv1}、\texttt{init\_garr1} 在 \texttt{.data} 中使用 \texttt{.string}、\texttt{.long} 等伪指令初始化；二是 \texttt{uninit\_gstr2}、\texttt{uninit\_gv2} 等变量在 \texttt{.bss} 中通过 \texttt{.zero} 预留空间；三是字符串常量以 \texttt{.LCx} 标签形式进入 \texttt{.rodata}；四是函数调用通过将参数依次装入 \texttt{\%edi}、\texttt{\%esi}、\texttt{\%rdi} 等寄存器，再执行 \texttt{call} 指令完成控制转移。

\noindent\textbf{4.实验结果：}分析结果表明，已初始化全局变量通常进入 \texttt{.data} 段，未初始化全局变量通常进入 \texttt{.bss} 段，字符串常量通常进入 \texttt{.rodata} 段，而带地址初值的全局指针变量则进入带重定位属性的数据段如 \texttt{.data.rel.local} 或 \texttt{.data.rel}。同时，汇编中的函数调用准确体现了 x86-64 System V ABI 约定：前几个整型或指针参数优先通过寄存器传递，返回值通过 \texttt{\%eax/\%rax} 返回。该阶段说明，汇编程序并不是对 C 代码的逐字符翻译，而是把变量存储期、可见性和调用语义重组为节、符号和指令三个层面的机器级表示。

\subsubsection{阶段2：可重定位目标文件解析}
\noindent\textbf{1.任务描述：}本阶段要求生成 \texttt{main.o} 并结合 \texttt{readelf}、\texttt{objdump}、\texttt{hexdump} 等工具，分析节头表、数据节、符号表、重定位节和只读节中的具体内容，说明一个全局变量定义语句在可重定位目标文件中会留下哪些信息。

\noindent\textbf{2.实验设计：}为了避免只看到零散命令输出而缺乏整体逻辑，本阶段采用“先节头表、再数据节、再重定位、最后符号表”的分析路径。其核心思想是：先用节头表建立文件的全局结构，再用 \texttt{.data/.bss/.rodata} 解释变量和常量的静态存储位置，再通过 \texttt{.rela.text}、\texttt{.rela.data.rel.local}、\texttt{.rela.data.rel} 等节解释为什么某些地址在编译阶段还不能确定，最后借助 \texttt{.symtab} 与 \texttt{.strtab} 将“二进制中的字节布局”与“源程序中的符号含义”重新对应起来。

\noindent\textbf{3.实验过程：}首先执行 \texttt{gcc -c -g -D U2 main.c -o main.o} 生成可重定位目标文件，然后用 \texttt{readelf -S -W main.o} 查看节头表，确认 \texttt{main.o} 中包含 \texttt{.text}、\texttt{.data}、\texttt{.bss}、\texttt{.rodata}、\texttt{.symtab}、\texttt{.strtab} 和多类 \texttt{.rela.*} 节。随后用 \texttt{readelf -x .data main.o} 验证 \texttt{init\_gv1=10}、\texttt{init\_gstr1="U202490042"}、\texttt{init\_garr1={11,12,13}} 和 \texttt{gv=6} 的实际字节排列；再用 \texttt{readelf -s main.o} 观察 \texttt{init\_gv1}、\texttt{init\_gstr1}、\texttt{init\_garr1}、\texttt{gv} 等符号的 \texttt{Value} 与节内偏移之间的对应关系。之后继续查看 \texttt{.bss} 中的未初始化变量、\texttt{.data.rel.local} 和 \texttt{.data.rel} 中的带地址初值变量，以及 \texttt{.rela.text} 中对外部函数和全局地址访问形成的重定位条目。

\noindent\textbf{4.实验结果：}实验结果显示，\texttt{main.o} 中共有 27 个主要节，其中 \texttt{.text} 负责存放代码，\texttt{.data} 负责存放已初始化普通全局变量，\texttt{.bss} 负责未初始化全局变量和静态局部变量，\texttt{.rodata} 负责只读常量，\texttt{.rela.*} 节则保存链接时需要修正的位置和符号信息。以 \texttt{.data} 节为例，十六进制转储中的 \texttt{0a000000}、\texttt{553230323439303034320000}、\texttt{0b000000 0c000000 0d000000} 与源程序里的 \texttt{init\_gv1}、\texttt{init\_gstr1}、\texttt{init\_garr1} 一一对应。这说明一个全局变量定义语句并不会只在目标文件中留下“一个地方”的痕迹，而是会同时在数据节、符号表、字符串表甚至重定位节中产生可追踪的信息。

\subsubsection{阶段3：可执行目标文件解析}
\noindent\textbf{1.任务描述：}本阶段要求分别以 \texttt{main.c sub.c} 和 \texttt{sub.c main.c} 的顺序链接生成 \texttt{main\_sub} 与 \texttt{sub\_main}，比较它们在函数排列、全局变量地址、符号表地址和反汇编结果上的差异，并据此说明链接时符号地址的确定规律以及可执行文件相对于可重定位目标文件的本质变化。

\noindent\textbf{2.实验设计：}本阶段采用“同源不同顺序”的对照法。由于两个可执行文件使用的源代码完全相同，唯一改变的是输入目标文件的链接顺序，因此观察到的地址差异可以直接归因于节合并顺序和链接器的符号布局策略。实验重点从三个角度展开：一是比较 \texttt{nm -n} 输出中函数和全局变量的排列顺序，说明链接器如何按输入文件顺序拼接同类节；二是比较 \texttt{readelf -s} 中可重定位目标文件的节内偏移与可执行文件中的最终虚拟地址；三是比较 \texttt{objdump -dr main.o} 与 \texttt{objdump -d main\_sub} 中同一段 \texttt{main} 函数代码，说明重定位前后的机器码差异。

\noindent\textbf{3.实验过程：}实验先执行 \texttt{gcc -g -D U2 main.c sub.c -o main\_sub} 和 \texttt{gcc -g -D U2 sub.c main.c -o sub\_main} 生成两个顺序不同的可执行文件，再用 \texttt{nm -n} 按地址排序查看符号。结果显示，在 \texttt{main\_sub} 中 \texttt{fcount}、\texttt{fsub}、\texttt{main} 先于 \texttt{fadd}、\texttt{check\_gcc\_condition} 排列，而在 \texttt{sub\_main} 中顺序恰好相反；数据段中 \texttt{init\_gv1}、\texttt{init\_gstr1}、\texttt{gv} 的最终地址也随链接顺序而变化。随后通过 \texttt{readelf -s main.o} 与 \texttt{readelf -s main\_sub} 对照同名符号，确认可重定位目标文件中的 \texttt{Value} 只是节内偏移，而可执行文件中的值已经是最终虚拟地址。最后比较 \texttt{objdump -dr main.o} 与 \texttt{objdump -d main\_sub}，观察 \texttt{call} 和 \texttt{lea} 指令中原来的占位字段如何被实际相对位移替换。

\noindent\textbf{4.实验结果：}结果表明，链接器会先合并多个目标文件中的同类节，再按输入目标文件顺序在节内依次拼接内容，因此符号最终地址并非只由源代码定义位置决定，也受链接输入顺序影响。对 \texttt{main.o} 而言，\texttt{fcount}、\texttt{main}、\texttt{init\_gv1} 等符号的值只是相对于 \texttt{.text} 或 \texttt{.data} 的偏移；而在 \texttt{main\_sub} 或 \texttt{sub\_main} 中，它们已经变成最终映像中的真实地址。与此同时，\texttt{main.o} 里原本仍携带 \texttt{R\_X86\_64\_PC32}、\texttt{R\_X86\_64\_PLT32} 等重定位条目的位置，在可执行文件中已经被具体机器码修正完成。这说明生成可执行文件的本质，就是把多个目标文件的节、符号和待定地址整合进同一地址空间，并通过重定位把所有“尚未填完的半成品代码”落实为可执行映像。

\subsubsection{阶段4：静态链接与动态链接生成执行程序的比较}
\noindent\textbf{1.任务描述：}本阶段要求同时生成动态链接版 \texttt{main\_sub\_dyn} 和静态链接版 \texttt{main\_sub\_static}，从文件大小、运行时依赖、ELF 内部结构以及库函数调用路径等角度比较两种链接方式生成程序的差异。

\noindent\textbf{2.实验设计：}阶段4的设计重点是从“程序里有没有包含库实现”和“运行时还需不需要系统继续补全地址”这两个根本问题出发。实验分别用 \texttt{ls -lh} 对比文件大小，用 \texttt{file} 和 \texttt{ldd} 判断程序对共享库的依赖情况，用 \texttt{readelf -d} 查看是否存在动态段，用 \texttt{objdump -d} 观察对 \texttt{printf} 的调用究竟是经过 \texttt{@plt} 还是直接进入库函数实现，从而把静态链接和动态链接的差异落实到可见证据上。

\noindent\textbf{3.实验过程：}实验依次执行 \texttt{gcc -g -D U2 main.c sub.c -o main\_sub\_dyn} 与 \texttt{gcc -g -static -D U2 main.c sub.c -o main\_sub\_static}。随后通过 \texttt{ls -lh} 观察两者大小，得到动态链接版约为 20K，静态链接版约为 884K；再通过 \texttt{file} 和 \texttt{ldd} 验证前者是 \texttt{dynamically linked} 且依赖 \texttt{libc.so.6}，后者是 \texttt{statically linked} 且 \texttt{ldd} 提示 \texttt{not a dynamic executable}。接着查看 \texttt{readelf -d} 的结果，确认动态链接版包含 \texttt{NEEDED}、\texttt{PLTGOT}、\texttt{JMPREL} 等动态段信息，而静态链接版没有动态段。最后对 \texttt{fcount} 中的 \texttt{printf} 调用进行反汇编比较，发现动态链接版调用的是 \texttt{printf@plt}，静态链接版则直接调用程序内部并入的 \texttt{\_IO\_printf}。

\noindent\textbf{4.实验结果：}实验表明，动态链接程序体积更小，因为它只保存用户程序本身的代码和共享库定位所需的元数据；静态链接程序体积显著更大，因为它把所需库函数实现直接打包进可执行文件内部。动态链接程序在运行时仍依赖共享库和动态加载器，因此 ELF 内部保留 \texttt{.dynsym}、\texttt{.dynstr}、\texttt{.rela.plt}、\texttt{.dynamic} 等结构；静态链接程序则不再需要这些动态解析辅助节。从调用路径上看，动态链接依赖 \texttt{PLT/GOT} 完成共享库函数定位，而静态链接直接调用已并入程序的库函数实现。这说明两种链接方式在文件大小、程序独立性、共享能力和后续更新维护方式上都具有本质区别。

\subsubsection{阶段5：动态链接库中的函数定位方法}
\noindent\textbf{1.任务描述：}本阶段要求以 \texttt{printf} 为例，说明动态链接库函数的地址不是在编译时就固定下来的，而是通过 \texttt{未定义符号 -> PLT 入口 -> GOT 槽位 -> 动态重定位 -> 动态加载器解析} 这一链条在装载时或调用前被补全。

\xfig{lab5-pltgot}{动态链接中借助 PLT 与 GOT 实现库函数延迟绑定与解析的过程示意图}{\resizebox{0.85\textwidth}{!}{\input{images/lab5-pltgot.tikz}}}

\noindent\textbf{2.实验设计：}为了避免把 \texttt{PLT/GOT} 讲成孤立概念，本阶段采用分层追踪法。首先在 \texttt{main.o} 中确认 \texttt{printf} 只是一个未定义外部符号；随后在动态链接可执行文件中找到用户代码对 \texttt{printf@plt} 的调用，再跟踪 \texttt{printf@plt} 如何通过 \texttt{jmp *GOT} 间接跳转；接着查看 \texttt{readelf -r} 和 \texttt{objdump -R} 中与 \texttt{printf} 对应的 \texttt{R\_X86\_64\_JUMP\_SLOT} 重定位项；最后用 \texttt{ldd} 和 \texttt{readelf -d} 说明动态加载器与 \texttt{libc.so.6} 在这个过程中分别扮演什么角色。

\noindent\textbf{3.实验过程：}实验先查看 \texttt{readelf -s main.o}，确认 \texttt{printf} 的 \texttt{Ndx=UND}，说明它在可重定位目标文件里只是一个未定义符号。然后转向 \texttt{main\_sub\_dyn}，在 \texttt{objdump -d} 中观察到用户代码调用的是 \texttt{printf@plt} 而不是直接调用 \texttt{printf}。进一步反汇编 \texttt{printf@plt} 可以看到，它通过 \texttt{jmp *...(\%rip)} 跳向 GOT 表中的对应槽位。接着查看 \texttt{readelf -r main\_sub\_dyn} 与 \texttt{objdump -R main\_sub\_dyn}，发现 \texttt{printf} 对应条目类型为 \texttt{R\_X86\_64\_JUMP\_SLOT}。最后结合 \texttt{ldd main\_sub\_dyn} 和 \texttt{readelf -d main\_sub\_dyn}，确认该程序依赖 \texttt{/lib64/ld-linux-x86-64.so.2} 与 \texttt{libc.so.6}，且当前实验环境中带有 \texttt{BIND\_NOW} 标志，因此符号通常在程序启动阶段就已完成解析。

\noindent\textbf{4.实验结果：}这一阶段表明，\texttt{printf} 的真实地址并不会直接写死在用户程序代码中，而是先在可重定位目标文件中以未定义符号形式存在，在动态链接可执行文件中获得一个 \texttt{printf@plt} 入口和一个 GOT 槽位，再由动态加载器根据 \texttt{libc.so.6} 中的导出符号把真实地址写入 GOT。此后用户代码执行 \texttt{call printf@plt} 时，就能间接跳转到动态库中的实际实现。也就是说，动态链接库函数的定位不是“代码里直接存着最终地址”，而是“代码、表项和重定位元数据共同配合动态加载器完成定位”。这也是动态链接能够在不把库实现直接拷入程序内部的前提下，仍然正确调用外部库函数的根本原因。

\subsection{实验小结}
本次实验按照“汇编程序、可重定位目标文件、可执行文件、链接方式比较、动态函数定位”五个阶段逐层展开，把同一份源程序在编译和链接流水线中的关键中间产物全部串联起来分析。阶段1让我看到变量和调用语义在汇编层如何落到伪指令、寄存器和寻址方式上；阶段2说明一个全局变量定义语句实际上会在数据节、符号表、字符串表和重定位节中同时留下痕迹；阶段3进一步说明链接器如何把多个目标文件的同类节合并、解析外部符号并完成重定位；阶段4和阶段5则把分析范围从“本程序内部结构”扩展到“与共享库、动态加载器的交互机制”，从而把静态链接、动态链接以及 \texttt{PLT/GOT} 机制联系起来理解。

从理论与方法上看，本实验最重要的价值在于把 ELF 文件与链接理论转化成了一组可验证的文件结构事实。过去对 \texttt{.text}、\texttt{.data}、\texttt{.bss}、\texttt{.symtab}、\texttt{.rela.text} 等节的理解更多停留在概念层面，而这次通过 \texttt{readelf}、\texttt{objdump} 和 \texttt{nm} 的逐项观察，我能够直接把“节、符号、重定位、动态段、GOT、PLT”与具体的地址、字节和指令位置建立对应关系，也更清楚地理解了为什么链接顺序会改变符号地址、为什么未定义符号能够在链接后获得最终地址、以及为什么动态链接程序可以在体积更小的同时依赖共享库实现函数调用。

本次实验的主要收获有三点。第一，我对从源程序到可执行程序这一完整构建链路形成了更清晰的整体认识，理解了每个阶段产物各自承担的职责。第二，我掌握了通过 \texttt{readelf}、\texttt{objdump}、\texttt{nm}、\texttt{ldd} 互相印证的分析方法，而不是只依赖单个工具片面判断。第三，我对静态链接与动态链接、以及动态加载器如何借助 \texttt{PLT/GOT} 定位库函数有了更扎实的机器级理解。后续若继续完善本实验，还可以把相关截图进一步整理成“同一符号在不同阶段文件中的连续证据链”，并补充对 PIC、延迟绑定与立即绑定差异的更细致讨论，使分析更加系统完整。
