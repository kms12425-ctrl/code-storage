# 任务五 动态链接库中的函数定位方法答案

## 研究动态链接库中的函数（如 `printf`）的定位方法

为了研究动态链接库函数的定位方法，可以继续使用动态链接生成的可执行文件，例如：

```bash
gcc -g -D U2 main.c sub.c -o main_sub_dyn
```

然后结合以下命令观察：

```bash
readelf -s main.o
readelf -s main_sub_dyn
objdump -d main_sub_dyn
readelf -r main_sub_dyn
objdump -R main_sub_dyn
readelf -S -W main_sub_dyn
ldd main_sub_dyn
```

结合本实验结果，可以把 `printf` 的定位过程分成以下几个层次来理解。

### 1. 在可重定位目标文件中，`printf` 只是一个未定义符号

在 `main.o` 中查看符号表可以看到：

```text
26: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND printf
```

这说明在编译 `main.c` 时，编译器只知道程序中调用了 `printf`，但并不知道它的最终地址在哪里。原因很简单：`printf` 并不在 [main.c](main.c) 或 [sub.c](sub.c) 中定义，而是由 C 标准库提供。

因此，在可重定位目标文件阶段，`printf` 只是一个外部未定义符号，真正的地址解析要留到后续链接和装载阶段。

### 2. 在动态链接可执行文件中，程序先调用 `printf@plt`

在动态链接可执行文件 `main_sub_dyn` 中，`fcount` 函数的反汇编片段如下：

```text
11fa: 48 8d 05 07 0e 00 00    lea    0xe07(%rip),%rax
1201: 48 89 c7                mov    %rax,%rdi
1204: b8 00 00 00 00          mov    $0x0,%eax
1209: e8 b2 fe ff ff          call   10c0 <printf@plt>
```

可以看到，这里并不是直接 `call printf`，而是先调用 `printf@plt`。其中 `PLT` 是 Procedure Linkage Table，也就是过程链接表。它的作用是为动态链接函数提供一个统一的跳转入口。

也就是说，在生成动态链接可执行文件时，链接器并不会把 `printf` 的真实实现直接拷贝到程序中，而是在程序的 `.plt` 节中为它准备一个入口。程序真正调用时，先进入这个入口，再由它跳转到 `printf` 的真实地址。

### 3. `printf@plt` 通过 GOT 表项间接跳转

`printf@plt` 自身的反汇编如下：

```text
00000000000010c0 <printf@plt>:
    10c0: f3 0f 1e fa                    endbr64
    10c4: f2 ff 25 fd 2e 00 00          bnd jmp *0x2efd(%rip)        # 3fc8 <printf@GLIBC_2.2.5>
```

这条 `jmp *0x2efd(%rip)` 的本质，是通过一个内存单元间接跳转。这个内存位置 `0x3fc8` 就是 `printf` 对应的 GOT 表项。

`GOT` 是 Global Offset Table，也就是全局偏移表。对于动态链接函数来说，GOT 中对应表项会保存该函数的实际入口地址。因此这里的控制流可以理解为：

- 用户代码先 `call printf@plt`
- `printf@plt` 再从 GOT 中取出 `printf` 的真实地址
- 最终跳转到动态库中的 `printf`

所以，`PLT` 负责提供代码入口，`GOT` 负责保存最终地址，它们是配合使用的。

### 4. 动态重定位表记录了 `printf` 的解析任务

`readelf -r main_sub_dyn` 和 `objdump -R main_sub_dyn` 可以看到与 `printf` 对应的重定位项：

```text
000000003fc8  R_X86_64_JUMP_SLOT  printf@GLIBC_2.2.5
```

这条记录说明：

- `0x3fc8` 这个 GOT 槽位对应的是 `printf`
- 重定位类型是 `R_X86_64_JUMP_SLOT`
- 这个槽位的值需要由动态链接器在装载时或调用前进行修正

与此同时，在 ELF 文件中还能看到与动态链接相关的节：

- `.dynsym`
- `.dynstr`
- `.rela.plt`
- `.rela.dyn`
- `.dynamic`

这些节共同保存了“需要解析哪些外部符号”“这些符号的名字是什么”“应该修正哪个 GOT/PLT 位置”等信息。也就是说，程序本身已经把“怎么找 `printf`”这件事所需的元数据准备好了，只等动态链接器来执行最后一步。

### 5. 动态链接器根据共享库信息把 `printf` 的真实地址写入 GOT

通过 `ldd main_sub_dyn` 可以看到，该程序依赖：

- `/lib64/ld-linux-x86-64.so.2`
- `libc.so.6`

其中：

- `ld-linux-x86-64.so.2` 是动态加载器；
- `libc.so.6` 是提供 `printf` 实现的共享库。

程序装载时，动态加载器会读取可执行文件中的 `.dynamic`、`.dynsym`、`.rela.plt` 等信息，找到 `printf@GLIBC_2.2.5` 对应的共享库实现地址，再把这个地址写入 GOT 中 `printf` 对应的槽位，也就是前面看到的 `0x3fc8`。

这样一来，之后程序再执行 `call printf@plt` 时，`printf@plt` 就能通过 GOT 直接跳到 `libc.so.6` 中真正的 `printf`。

### 6. 本实验环境下是“启动时解析”，而不是第一次调用时再解析

从动态段信息中还可以看到，本实验中动态链接版带有 `BIND_NOW` 标志。这意味着该程序在启动装载时就会把相关动态符号提前解析好，而不是等第一次真正调用 `printf` 时才去解析。

因此，虽然教材中经常把 `PLT/GOT` 解释成“第一次调用时解析、以后直接跳转”，这个原理本身没有错，但在本实验当前生成的二进制里，更准确的说法是：

- `printf` 仍然是通过 `PLT + GOT + 动态重定位` 机制定位的；
- 但具体解析时机由于开启了 `BIND_NOW`，通常会提前到程序启动阶段。

### 总结

动态链接库中的函数，如 `printf`，并不是在编译阶段就确定最终地址的。其定位过程通常是：在可重定位目标文件中先把 `printf` 记为未定义外部符号；在动态链接可执行文件中为它建立 `printf@plt` 入口，并在 GOT 中预留相应槽位；同时在 `.rela.plt` 等动态重定位表中记录该槽位需要被解析为 `printf@GLIBC_2.2.5` 的真实地址；最后由动态加载器在程序装载时根据 `libc.so.6` 完成解析，并把真实地址写入 GOT。这样，程序中的 `call printf@plt` 最终就能够跳转到动态链接库中的 `printf` 实现。这就是动态链接库函数定位的基本方法。
