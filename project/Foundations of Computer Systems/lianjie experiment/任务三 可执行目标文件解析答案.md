# 任务三 可执行目标文件解析答案

## 1. `main_sub` 与 `sub_main` 中符号排列顺序及地址确定规律

实验命令：

```bash
gcc -g -D U2 main.c sub.c -o main_sub
gcc -g -D U2 sub.c main.c -o sub_main
nm -n main_sub
nm -n sub_main
```

从按地址排序的符号表可以看出，两个可执行文件中函数与全局变量的排列顺序并不相同。

`main_sub` 中的主要函数顺序为：

- `fcount`：`0x11c9`
- `fsub`：`0x1211`
- `main`：`0x12c0`
- `fadd`：`0x13c4`
- `check_gcc_condition`：`0x141c`

对应的主要全局变量顺序为：

- `init_gv1`：`0x4010`
- `init_gstr1`：`0x4018`
- `gv`：`0x4034`
- `extern_int`：`0x4050`
- `uninit_gv2`：`0x4060`

`sub_main` 中的主要函数顺序为：

- `fadd`：`0x11c9`
- `check_gcc_condition`：`0x1221`
- `fcount`：`0x1313`
- `fsub`：`0x135b`
- `main`：`0x140a`

对应的主要全局变量顺序为：

- `extern_int`：`0x4010`
- `init_gv1`：`0x4018`
- `init_gstr1`：`0x4020`
- `gv`：`0x403c`
- `uninit_gv2`：`0x4060`

从这两个结果可以看出，链接时符号地址的确定与输入目标文件的顺序密切相关。在 `main_sub` 中，由于 `main.c` 对应的目标文件先参与链接，因此来自 `main.o` 的 `.text`、`.data` 中的内容整体更靠前；而在 `sub_main` 中，由于 `sub.c` 对应的目标文件先参与链接，所以 `sub.o` 中的函数和数据会优先占据较低地址。

因此，可以把规律概括为：链接器会先合并同类节，例如把多个目标文件的 `.text` 合并为一个连续代码段、把多个目标文件的 `.data` 合并为一个连续数据段；在同类节内部，通常按输入目标文件顺序依次拼接，符号最终地址也就随之确定。

## 2. 可执行文件符号表中地址与可重定位目标文件中地址的差异

实验命令：

```bash
readelf -s main.o
readelf -s main_sub
readelf -s sub_main
```

在可重定位目标文件 `main.o` 中，符号表中的 `Value` 往往只是“该符号在所属节中的偏移量”，并不是最终的运行地址。例如：

- `fcount` 的值为 `0x0`
- `fsub` 的值为 `0x48`
- `main` 的值为 `0xf7`
- `init_gv1` 的值为 `0x0`
- `init_gstr1` 的值为 `0x8`
- `gv` 的值为 `0x24`

这些值都只是相对于 `.text` 或 `.data` 等节起始位置的偏移。

而在可执行文件中，符号地址已经变成最终映像中的虚拟地址。例如在 `main_sub` 中：

- `fcount = 0x11c9`
- `main = 0x12c0`
- `init_gv1 = 0x4010`
- `init_gstr1 = 0x4018`
- `gv = 0x4034`

在 `sub_main` 中，这些地址又会因为链接顺序变化而发生改变，例如：

- `fcount = 0x1313`
- `main = 0x140a`
- `init_gstr1 = 0x4020`
- `gv = 0x403c`

此外，在 `main.o` 中原本是未定义符号的 `fadd`、`check_gcc_condition`、`extern_int`，到了可执行文件中已经被解析成具体地址，因为它们的定义来自另一个目标文件；而像 `printf` 这样的库函数，由于最终采用动态链接方式解析，其实现并不会直接作为普通本地函数出现在本程序的代码段中。

因此，可重定位目标文件与可执行目标文件中符号地址的根本差别在于：前者表示节内偏移，后者表示链接完成后的最终地址。

## 3. `main` 函数在可执行文件与可重定位目标文件中的差别

实验命令：

```bash
objdump -dr main.o
objdump -d main_sub
objdump -d sub_main
```

在 `main.o` 中，`main` 函数内很多指令仍然保留着待修正的占位值。例如：

```text
103: 48 8d 05 00 00 00 00    lea    0x0(%rip),%rax
                     106: R_X86_64_PC32 init_gstr1-0x4
10d: e8 00 00 00 00          call   112 <main+0x1b>
                     10e: R_X86_64_PLT32 check_gcc_condition-0x4
117: e8 00 00 00 00          call   11c <main+0x25>
                     118: R_X86_64_PLT32 fcount-0x4
```

这里可以看到两种明显特征：

- 机器码中出现了大量 `00 00 00 00` 这样的占位字段；
- 反汇编结果旁边附带了重定位信息，说明这些位置在链接时还要被修正。

而在 `main_sub` 中，对应位置已经变成了最终结果：

```text
12cc: 48 8d 05 45 2d 00 00    lea    0x2d45(%rip),%rax        # 4018 <init_gstr1>
12d6: e8 41 01 00 00          call   141c <check_gcc_condition>
12e0: e8 e4 fe ff ff          call   11c9 <fcount>
```

这说明链接器已经根据符号的最终地址，把原先的占位字段改写成真实的相对位移。于是，可执行文件中的机器码不再需要依赖 `.rela.text` 这类重定位条目来解释当前这些位置该填什么值。

不过，也不是 `main.o` 中所有指令都必须留到链接时再改。例如 `main` 中调用 `fsub` 的指令，在 `main.o` 中就已经具有确定的相对位移。这是因为 `fsub` 是 `static` 局部函数，定义和调用都在同一个目标文件、同一个代码节中，编译阶段就能确定它们之间的相对距离。

因此，可重定位目标文件中的 `main` 更像“尚未填完地址字段的半成品代码”，而可执行文件中的 `main` 则是“地址已经最终落实的可运行代码”。

## 4. 符号定义、符号绑定、符号引用、重定位的基本概念

这四个概念可以结合本实验中的具体例子来理解。

- 符号定义

  符号定义是指某个目标文件真正提供了该符号对应的代码或数据实体。例如 [main.c](main.c#L23) 中定义了 `fcount`，[main.c](main.c#L42) 中定义了 `main`，[sub.c](sub.c#L8) 中定义了 `fadd`，[sub.c](sub.c#L6) 中定义了 `extern_int`。这些都属于符号定义。

- 符号绑定

  符号绑定描述的是符号的可见范围和链接属性。最常见的是 `LOCAL` 和 `GLOBAL`。例如 [main.c](main.c#L32) 中的 `fsub` 被声明为 `static`，因此它在符号表中是局部绑定，只在本目标文件内部可见；而 `fcount`、`main`、`init_gv1` 等则是全局绑定，可以被其他目标文件看到。

- 符号引用

  符号引用是指当前目标文件使用了某个符号，但该符号并未在当前文件中定义。例如 [main.c](main.c#L58) 中调用了 `fadd`，[main.c](main.c#L44) 中调用了 `check_gcc_condition`，[main.c](main.c#L56) 中使用了 `extern_int`。这些都会在 `main.o` 中形成对外部符号的引用。

- 重定位

  重定位是指链接器根据符号的最终地址，对代码和数据中的相关字段进行修正。例如 `main.o` 中访问 `init_gstr1` 的 `lea` 指令、调用 `fcount` 和 `check_gcc_condition` 的 `call` 指令，在编译阶段都只是先留下占位值；链接器在生成可执行文件时，再把这些占位值改成正确的相对位移或目标地址，这个过程就是重定位。

因此，这四个概念实际上构成了链接过程的核心逻辑：先区分哪些符号是定义、哪些是引用，再根据绑定属性确定可见范围，最后通过重定位把引用真正落实到最终地址上。

## 5. 生成可执行程序的基本过程

结合本实验，可以把从多个目标文件到最终可执行文件的过程概括为以下几步。

### 5.1 编译生成可重定位目标文件

首先，编译器分别把 [main.c](main.c) 和 [sub.c](sub.c) 编译成各自的目标文件。每个目标文件内部都有自己的 `.text`、`.data`、`.bss`、`.rodata`、`.symtab`、`.rela.text` 等节。

### 5.2 合并同类节

链接器把多个目标文件中的同类节进行合并，例如把 `main.o` 和 `sub.o` 中的 `.text` 合并成最终代码段，把 `.data` 合并成最终已初始化数据段，把 `.bss` 合并成最终未初始化数据段。在这一阶段，输入目标文件顺序会影响最终段内内容的排列顺序。

### 5.3 解析符号

链接器接着扫描各个目标文件的符号表，把一个文件中的未定义符号与另一个文件中的已定义符号配对起来。例如 `main.o` 中对 `fadd`、`check_gcc_condition`、`extern_int` 的引用，都会在 `sub.o` 中找到对应定义。

### 5.4 完成重定位

在得到各个符号的最终地址后，链接器再根据 `.rela.text`、`.rela.data` 等重定位信息，修正代码和数据中原先尚未确定的地址字段。这样，原来在可重定位目标文件中尚未完成的指令和数据项，就变成了最终可执行形式。

### 5.5 生成最终可执行文件

最后，链接器生成完整的 ELF 可执行文件，并保留必要的运行时信息。对于像 `printf` 这样的库函数，如果采用动态链接方式，链接器不会把其实现代码直接拷入本程序，而是保留相应的动态链接入口，等程序装载运行时再完成最终定位。

因此，生成可执行程序的本质，就是把多个目标文件中的节和符号组织成一个统一的地址空间，并通过符号解析与重定位把原本分散、未完成的代码和数据连接成一个可以装载运行的整体。
